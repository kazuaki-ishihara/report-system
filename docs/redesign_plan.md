## 1. 背景と目的

### 1.1 現状の見立て

画面の構成と内容から、**課ごとに Excel で集めている月次の現状報告を Web に置き換える**ためのシステムと考えられる。

現行（`main`）の作りは次のとおりで、部下の入力負担が Excel 運用より増えるおそれがある。

| 現行の作り | 問題 |
|---|---|
| 毎回、白紙から 6 項目を入力する | 前月から変わらない内容も毎月打ち直しになる |
| 「氏名」「日付」を手入力する | ログイン情報や対象月から自動で決められる |
| 「課題」が自由記述の 1 欄 | 継続中の課題を毎月書き写す。解決したかを追えない |
| 下書きと提出の区別がない | 途中保存できず、一度に書き上げる必要がある |
| 上司側は一覧と検索だけ | 未提出者がわからない。横並びの比較・集計ができない |
| 項目が 6 つで固定（11 ファイルに直書き） | 課ごとに異なる補足情報を集められない |

### 1.2 目的

1. **部下の入力負担を Excel 運用以下にする**（前月引き継ぎ、自動入力、下書き）
2. **課ごとに異なる様式・情報収集に対応する**（共通項目＋課別項目、項目マスタで自由に設定）
3. **課長・確認者の確認と、課長の報告資料づくりを楽にする**（提出状況、横並び表示、資料用の出力）
4. 見た目を全面的に見直す
5. **客先の情報を守る**（守秘義務。§11）

### 1.2.1 システムの範囲

- このシステムは、**課の中の情報（元ネタ）を集約し、課長が報告しやすくする**ためのもの。
- 報告の流れは**課長で完結する**。課長より上（部長・役員など）への報告書は、課長がこのシステムの出力（§11.7）をもとに別に作る。部長・役員はこのシステムを使わない。

### 1.3 設計の原則：部下の作業を増やさない

報告の作成は時間外の作業になりがちなため、**部下の手戻り・やり直しを生む仕組みは入れない**。

- **差戻しはしない。** 報告全体を突き返して再提出させる機能は作らない。
- 不明点はコメントで聞くが、**回答がなくても確認を止めない**（回答待ちのコメントがあっても「確認完了」にできる）。
- 提出後に部下が追記しても、**再提出の操作は不要**（変更履歴が残り、確認者に「更新あり」と表示されるだけ）。
- 必須項目は最小限にし、下書き保存では必須チェックをしない。
- 前月の内容の引き継ぎ・自動入力で、毎月の入力量を減らす。
- 新しい機能を足すときは「部下の作業が増えないか」を確認する。

### 1.4 設計の原則：漏えいは起きる前提で、起きたときの被害を小さくする

情報漏えいは防ぎきれない前提で設計する。**漏えいしても、守秘義務の違反になる範囲・謝罪の範囲が最小になる**ことを、設計の段階で判断材料に入れる（§11）。

| 考え方 | 内容 |
|---|---|
| 集めない | 必要なものだけ集める。客先名・案件名・個人名はこのシステムに入れない。自由記述より選択式 |
| 結び付けない | 案件はコードだけで扱い、客先との対応表はシステムの外に置く。DB だけが漏れても、どの客先の話か分からない |
| 読めなくする | 機密度の高い項目は暗号化して保存し、鍵は DB とは別の場所に置く。DB ファイルだけが漏れても読めない |
| 早く消す | 自由記述は一定期間で消し、集計に必要な選択式の値だけを残す |
| 範囲を特定できる | 誰が・いつ・何を見たか、出力したかを記録し、漏えい時に影響範囲をすぐ絞り込めるようにする |
| 出さない | CSV 等の出力を最小限にし、出力したファイルには出力者・日時を入れる |

新しい項目や機能を足すときは「これが漏れたら誰に謝ることになるか」を確認する。

### 1.5 設計の原則：月に 1 回しか使わない前提にする

報告は毎日ではなく**毎月 1 回**の作業である。部下は月に 1 回しかログインせず、使い方もパスワードも忘れている前提で設計する。

| 起きること | 対応 |
|---|---|
| 使い方を忘れる | 説明なしで使える画面にする。「今月の報告を作る」ボタン 1 つから始まり、前月の内容が入った状態で開く |
| パスワードを忘れる | 管理者に頼らずに再設定できるようにする（2 段階認証のコードで本人確認して再設定。§11.3.1） |
| 2 段階認証の端末の記憶が切れる | 記憶の期間を 1 か月より長くする（例: 90 日）。月 1 回の利用で毎回コードを求めないようにする |
| スマートフォンを機種変更している | 2 段階認証の再設定を、本人がほかの方法で本人確認できる形で行えるようにする（予備のコードを最初に発行する） |
| ロックされる | 試行回数の制限は「10 回失敗で 15 分」程度にゆるめ、月 1 回の利用者を締め出さない |
| 報告の時期を忘れる | 月初・締め日前にお知らせする（Q-10）。ホーム画面にも当月の締め日を表示する |
| 前月の内容を覚えていない | 前月の内容を引き継ぎ、変わったところだけ直す（F-09、F-20） |

確認者（課長・課長代理・リーダー）も、月末から月初にまとめて確認する使い方になると考えられる。提出状況の一覧で「自分が未チェックの報告」をまとめて順番に見られるようにする。

### 1.6 例外：月の途中で情報を集める場合

基本は月 1 回だが、**例外的に月の途中で情報を集める**ことがある。次の 2 つの型を想定する。**実態は主に型 B（臨時の調査）**。

| 型 | 例 | 対応 |
|---|---|---|
| A. 月の途中の状況更新 | 案件の終了が決まった、客先から増員の話が来た | **提出済みの月次報告に追記する**（§4.3。再提出は不要で、確認者に「更新あり」と表示される）。確認者から「最新の状況を更新してください」と**更新依頼**を出すこともできる |
| B. 臨時の調査 | 「来月から入れる人はいるか」「〇〇の経験者はいるか」など、月次報告にない質問を急ぎで聞く | **臨時の依頼**を作る。質問・対象者・回答期限を決めて送る。回答は月次報告とは別に集計する |

臨時の依頼（型 B）も §1.3（部下の作業を増やさない）に従う。

- 質問は少なく、選択式を基本にする（項目マスタと同じコントロールを使う）。
- 月次報告ですでに答えている内容は聞かない。必要なら最新の月次報告の値を回答欄に入れておく。
- 回答はスマートフォンで 1 分程度で終わる量にする。
- 回答の締め切りを過ぎたら依頼を閉じる。回答がなくても催促を繰り返さない。
- 臨時の依頼の回答も、機密区分・保管期限・閲覧の記録の対象にする（§11）。

#### 臨時の調査（型 B）の特徴と設計

集める情報は月次報告と大きくは変わらないが、**ときどき月次報告にない質問が入る**。例: 「AI を使ったことがあるか」「業務で使っているか」。こうした質問は、課の外（経営層や他部署など）からの依頼であることが多いと考えられる。

| 特徴 | 設計 |
|---|---|
| 月次報告と同じ情報が多い | 質問に**月次報告の項目をそのまま選べる**。回答欄には最新の月次報告の値を入れておき、変わっていなければそのまま送れる |
| ときどき違う質問がある | その依頼だけの**独自の質問**を足せる（コントロールは項目マスタと同じ 10 種類） |
| 依頼元が課の外のことがある | 依頼に**依頼元**（例: 経営企画、本社）と**目的**を書く欄を持つ。部下の画面にも「誰が・何のために聞いているか」を表示する |
| 課をまたいで聞くことがある | 対象を「全社」「課を指定」「人を指定」から選ぶ |
| 似た調査を繰り返す | 依頼を**ひな形として保存**し、次回はそれを複製して使う |
| 定着した質問がある | 臨時の質問を、あとから月次報告の項目（項目マスタ）に**移せる** |

**依頼を作る人と結果の渡し方**

- 臨時の依頼を作れるのは**課長だけ**（と管理者）。課の外からの依頼も、課長が受けて依頼を作る。
- 課の外の依頼元はこのシステムにログインしない。**課長が結果を出力し、資料にして渡す**（§11.7）。依頼元のアカウントを作らないので、見られる人が増えない。

**回答を誰が見られるか**（§1.4 漏えいを前提にした設計）

| 設定 | 内容 | 例 |
|---|---|---|
| 個別の回答を見られる人 | 依頼を作った人と、対象者の課の確認者・管理者 | 「来月から入れる人はいるか」 |
| 集計だけを見られる人 | 依頼元に、件数・割合だけを渡す（誰が何と答えたかは渡さない） | 「AI を業務で使っているか」 |

- 依頼元には、原則として**集計だけ**を渡す。個人ごとの回答が必要なときだけ、個別の回答の閲覧を許可する。
- 臨時の質問にも機密区分を付ける。

## 2. 前提・制約

| 項目 | 内容 |
|---|---|
| 稼働条件 | `main` と同じ。さくらのレンタルサーバ、PHP、SQLite（PDO）、フレームワークなし |

### 2.1 石原課長のブランチとの整合

統合しやすくするため、課長の設計を土台にして拡張する。

| 課長の設計 | 本計画での扱い |
|---|---|
| `report_fields`（code, label, field_type, sort_order, is_active, is_required） | **同じテーブル名・同じ列名**を使い、列を追加する（課、選択肢、引き継ぎ等） |
| `report_records` / `report_field_values` / `report_field_comments` | 同じテーブル名・同じ列名を使い、列を追加する（対象月、提出状態等） |
| 項目は削除不可・無効化で扱う（トリガー） | そのまま採用 |
| 項目の種類 3 つ（single_text, multi_text, date） | **同じ値を使い**、種類を追加する |
| 既存の reports / comments は移行しない | **移行する**（本番に既存データがあるため。§7） |
| 管理画面 `public/report_fields/`、CSRF は画面ごとのトークン | 管理画面の場所は合わせる。CSRF は全画面共通の仕組みにする |

## 4. 業務の流れ（案）

### 4.1 確認者は 1 課に複数いる

1 つの報告を、課の中の**複数の人が確認し、それぞれコメントする**。

| 確認者 | 人数（1 課あたりの目安） |
|---|---|
| 課長 | 1 名 |
| 課長代理 | 2 名 |
| リーダー | 2〜3 名 |

コメントは主に次の 2 つの目的で使われる。

| 目的 | 例 | 必要なこと |
|---|---|---|
| **追加情報の依頼** | 「この件の発生日と影響範囲を追記してください」 | 部下が回答・追記するまで「回答待ち」として残す |
| **認識の確認** | 「これは先月の○○の続きという理解でよいですか」 | 部下の返答で完了 |

そのため、次の 2 点を見えるようにする。

1. **誰がチェック済みで、誰が未チェックか**（報告ごと・確認者ごと）
2. **回答待ちのコメントがあるか**（部下・確認者の双方）

### 4.2 流れ

```text
部下                            確認者（課長・課長代理・リーダー）          管理者
 │ 1. 当月の報告を作成
 │    （前月の内容を自動で引き継ぎ）
 │ 2. 下書き保存（何度でも）
 │ 3. 提出 ──────────────────→ 4. 各確認者がそれぞれ内容を確認
 │                                  ・問題なければ「チェック済」
 │ ←──────────────────────── ・不明点は項目ごとにコメント
 │                                     （追加情報の依頼／認識の確認）
 │ 5. コメントに返信・報告を追記 ──→ 6. 返信を見て「解決」にする
 │                                  （追記で内容が変わったら、チェック済の人に「更新あり」と表示）
 │                                7. 最終確認者（課長）が「確認完了」
 │                                8. 提出状況・チェック状況の一覧、横並び表示、CSV 出力
 │                                                                      項目マスタ（共通）
 │                                課別項目の管理（課の管理者）             組織・ユーザー管理
```

### 4.3 報告の状態

| 状態 | 意味 | 部下の編集 |
|---|---|---|
| 下書き | 作成中 | 可 |
| 提出済 | 確認者のチェック中 | **追記・修正は可**（変更履歴を残し、チェック済の確認者に「更新あり」と表示） |
| 確認完了 | 最終確認者が完了にした | 不可 |

- **差戻しはしない**（§1.3）。不明点はコメント（追加情報の依頼）で聞き、必要な点だけやり取りする。
- 回答待ちのコメントが残っていても「確認完了」にできる。部下に回答を強制しない。

### 4.4 確認者ごとのチェック状況

| 表示 | 意味 |
|---|---|
| 未チェック | まだ見ていない |
| チェック済 | 確認した（日時を記録） |
| 更新あり | チェックしたあとに部下が報告を修正した（再確認が必要） |

報告の詳細画面に確認者ごとの状態を並べ、提出状況の一覧では「チェック済 3/6」のように件数で表示する。

### 4.5 コメントの状態

| 種類 | 状態の流れ |
|---|---|
| 追加情報の依頼 | 回答待ち → 回答あり → 解決（依頼した人が解決にする） |
| 認識の確認 | 回答待ち → 回答あり → 解決 |
| 連絡（返答不要） | 状態なし |

- コメントには部下や他の確認者が**返信できる**（スレッド形式）。
- 部下のホーム画面に「回答待ちのコメント n 件」、確認者のホーム画面に「自分の依頼への回答あり n 件」を表示する。

| F-13 | 前月との差分表示 | 前月から変わった項目を強調 | 3 |
| F-14 | 資料用の出力 | 課長が課外向けの資料を作る元ネタとして、対象月・課・臨時の調査を指定して出力。印刷用画面（ブラウザーで PDF 保存）、Excel 形式（.xlsx）、CSV（§11.7） | 3 |

## 6. 項目マスタ

### 6.1 項目ごとの設定

| 設定 | 内容 |
|---|---|
| 表示名 | 画面に出す名前 |
| コード | 内部用の識別子（英数字。作成後は変更不可） |
| 適用範囲 | 共通（全課）／特定の課 |
| コントロールの種類 | §6.2 |
| 並び順 | 様式内での順番（共通項目→課別項目の順に並べ、それぞれの中で並び順） |
| 必須 | 提出時に必須か（下書き保存では必須チェックをしない） |
| 説明文・入力例 | 入力欄の下・中に表示 |
| 選択肢 | プルダウン・ラジオ・チェックボックス用 |
| 入力制限 | 最大文字数、数値の最小・最大・小数桁 |
| 前月から引き継ぐ | ○ なら新しい月の報告に前月の値を入れる |
| 一覧に表示／検索対象／CSV に出力 | それぞれ ○／× |
| 有効・無効 | 無効にすると新しい報告には出ない。過去の報告には残る |

### 6.2 コントロールの種類

| 種類（field_type） | 画面 | 保存形式（value_text） | 備考 |
|---|---|---|---|
| `single_text` | 1 行テキスト | 文字列 | 課長のブランチと同じ値 |
| `multi_text` | 複数行テキスト | 文字列 | 同上 |
| `date` | 日付 | `YYYY-MM-DD` | 同上 |
| `month` | 年月 | `YYYY-MM` | |
| `number` | 数値 | 数字の文字列 | 最小・最大・小数桁 |
| `select` | プルダウン（1 つ選ぶ） | 選択肢のコード | |
| `radio` | ラジオボタン（1 つ選ぶ） | 選択肢のコード | |
| `checkbox` | チェック 1 つ（はい／いいえ） | `0` / `1` | |
| `multi_check` | チェックボックス（複数選ぶ） | JSON 配列 | |
| `table` | 繰り返し行（表形式。例: 課題一覧） | JSON 配列 | 列の定義を設定に持つ。列の種類は single_text / multi_text / number / date / select |

選択肢は「コード＋表示名」で持つ。表示名を変えても保存済みのデータは変わらない。

### 6.3 変更の制限（データを壊さないため）

| 操作 | データがない項目 | データがある項目 |
|---|---|---|
| 表示名・説明・並び順・必須の変更 | 可 | 可（過去の報告は作成当時の定義で表示） |
| 削除 | 不可（無効化のみ） | 不可（無効化のみ） |
| コントロールの種類の変更 | 可 | 互換のある変更のみ（1 行→複数行、プルダウン⇔ラジオ） |
| 選択肢の削除 | 可 | 不可（無効化のみ） |
| 適用範囲（共通⇔課）の変更 | 可 | 不可 |

### 6.4 様式の初期案（2 課の現行の報告内容から）

#### 現行の報告内容

| A課 | B課 |
|---|---|
| 現場作業状況（従事している案件が変わった、作業フェーズが変わったなど） | 現場作業状況（参画案件での担当内容と、作業状況：問題なく進行／問題発生による遅延） |
| 問題、悩み事など | — |
| 業務システムの種類（在庫管理、販売管理など） | — |
| フェーズ（設計段階、製造・単体など） | — |
| 終了時期 | 現在の案件の終了の話は出ているか。当分継続予定か |
| 終了時期以後の作業はあるか | — |
| 増員予定（削員予定を含む）はあるか | 客先で追加要員を探しているような話は聞いていないか |

両課とも、**「現場の状況」「案件がいつまで続くか」「人員が増えそうか減りそうか」** を集めている。違いは聞き方の細かさ。

#### 見立て

- 毎月の答えの多くは「前月から変わらない」。→ **前月の引き継ぎ＋「前月から変更なし」の一括操作**で、変化のない月は数クリックで終わるようにする。
- 自由記述をやめて**選択式にできる項目が多い**（フェーズ、進捗、継続見込み、増員の有無）。部下は選ぶだけになり、上司側は集計できる。
- 上司にとって価値が高いのは、**「終了が近い案件」「人員が増えそうな現場」「遅延・問題がある現場」をまとめて見られること**（§5 F-19）。

#### 共通項目（案）

1 人が同時に複数の案件に参画することがあるため、**案件ごとの項目は「案件ブロック」として繰り返し入力できる**ようにする（§6.5）。

| 区分 | 項目 | コントロール | 前月引き継ぎ | 必須 | 元になった質問 |
|---|---|---|---|---|---|
| 報告全体 | 前月からの変更 | チェック「変更なし」 | — | | （新規）オンにすると前月と同じ内容で提出できる |
| 案件ブロック | 案件 | **案件マスタから選ぶ**（社内の案件コード。客先名・案件名は書かない。§11.1） | ○ | ○ | 両課の「現場作業状況」 |
| 案件ブロック | 担当内容 | 複数行テキスト（客先名・固有名詞を書かない旨を説明文に表示） | ○ | | B課「担当内容」 |
| 案件ブロック | 作業フェーズ | プルダウン（要件定義／基本設計／詳細設計／製造・単体／結合テスト／総合テスト／運用・保守／その他） | ○ | | A課「フェーズ」 |
| 案件ブロック | 進捗 | ラジオ（問題なく進行／遅延あり／その他） | ○ | ○ | B課「作業状況」 |
| 案件ブロック | 進捗の補足 | 複数行テキスト（遅延・その他のときだけ記入） | | | 同上 |
| 案件ブロック | 案件の継続見込み | ラジオ（当分継続／終了の話あり／未定） | ○ | ○ | 両課の「終了時期」「終了の話」 |
| 案件ブロック | 終了予定 | 年月 | ○ | | A課「終了時期」 |
| 案件ブロック | 人員の動き | ラジオ（増員の話あり／減員の話あり／特になし／不明） | ○ | | A課「増員・削員予定」、B課「追加要員」 |
| 案件ブロック | 人員の動きの詳細 | 複数行テキスト | | | 同上 |

#### 課別項目（案）

| 課 | 区分 | 項目 | コントロール | 前月引き継ぎ |
|---|---|---|---|---|
| A課 | 報告全体 | 問題・悩み事 | 複数行テキスト | |
| A課 | 案件ブロック | 業務システムの種類 | プルダウン（在庫管理／販売管理／生産管理／会計／人事・給与／その他） | ○ |
| A課 | 案件ブロック | 終了後の作業 | ラジオ（あり／なし／不明） | ○ |
| B課 | 案件ブロック | 客先の追加要員の募集 | ラジオ（聞いている／聞いていない） | |

- 選択肢の中身は課長に確認して調整する（項目マスタで変更できる）。

### 6.5 案件ブロック（繰り返し入力）

- 項目を「報告全体」と「案件ブロック」の 2 つの区分に分ける。案件ブロックの項目は、参画している案件の数だけ繰り返して入力する。
- 前月の報告から、案件ブロックごと引き継ぐ。案件が終わったらそのブロックを外し、新しい案件に入ったらブロックを足す。
- 項目マスタで、項目ごとにどちらの区分にするかを設定する。
- 上司のまとめ表示（F-19）は、案件ブロック単位で集計する（例: 終了予定が 3 か月以内の案件の一覧）。

### 6.6 過去の報告の表示

報告を作成したときに、その時点の項目定義（表示名・種類・選択肢・並び順）を報告ごとに保存する（§8 の `report_record_fields`）。項目マスタをあとから変更しても、過去の報告は作成当時の見え方のまま表示する。

## 7. 既存データの移行

| 移行元（現行） | 移行先 | 方法 |
|---|---|---|
| `users` | `users`（列を追加） | `department_id`（所属課）を追加。初期値は未設定とし、管理画面で割り当てる |
| `reports` の 6 列 | `report_records` ＋ `report_field_values` | 6 項目を初期の共通項目として登録し、値を移す。対象月は `report_date` の年月 |
| `comments.field_name` | `report_field_comments.field_id` | `field_name`（report_date 等）を項目のコードで引き当てる。種類は「連絡」、返信なしとして移す |
| （なし） | `report_reviews` | 移行データはチェック状況なし（確認完了扱いにするかは Q-06 と合わせて決める） |
| `reports` / `comments` テーブル | 残す（名前を変えて退避） | 移行の検証が終わるまで残す |

- 現行のデータには、**同じユーザー・同じ月に 2 件**の報告がある（リポジトリ同梱の DB で 2 名）。移行したデータは「移行データ」として印を付け、1 人 1 か月 1 件の制約は新しく作る報告だけに適用する。
- 「氏名」「日付」は、新しい様式ではユーザー情報と対象月から自動で決めるため、共通項目としては無効にする。移行データの表示では残す。
- 移行は、必ず本番 DB のコピーで試してから行う。手順書と戻し方を用意する。

## 8. データベース設計（案）

課長のブランチのテーブルに列を追加する形。★ は本計画で追加するもの。

```sql
-- ★ 組織（課）
CREATE TABLE departments (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    is_active   INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1)),
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);

-- ★ users に所属課を追加（SQLite の ALTER TABLE ADD COLUMN で追加できる）
-- ALTER TABLE users ADD COLUMN department_id INTEGER REFERENCES departments(id);

-- ★ 課別項目を管理できるユーザー
CREATE TABLE department_admins (
    department_id INTEGER NOT NULL REFERENCES departments(id),
    user_id       INTEGER NOT NULL REFERENCES users(id),
    PRIMARY KEY (department_id, user_id)
);

-- 項目マスタ（課長の設計＋★の列）
CREATE TABLE report_fields (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    code           TEXT NOT NULL UNIQUE,
    label          TEXT NOT NULL,
    field_type     TEXT NOT NULL CHECK (field_type IN (
                       'single_text', 'multi_text', 'date', 'month', 'number',
                       'select', 'radio', 'checkbox', 'multi_check', 'table')),
    department_id  INTEGER REFERENCES departments(id),   -- ★ NULL = 共通項目
    field_scope    TEXT NOT NULL DEFAULT 'report'        -- ★ report=報告全体 / project=案件ブロック
                   CHECK (field_scope IN ('report', 'project')),
    confidentiality TEXT NOT NULL DEFAULT 'normal'       -- ★ 機密区分 normal=通常 / internal=社外秘 / restricted=限定
                   CHECK (confidentiality IN ('normal', 'internal', 'restricted')),
    sort_order     INTEGER NOT NULL DEFAULT 0,
    is_active      INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1)),
    is_required    INTEGER NOT NULL DEFAULT 0 CHECK (is_required IN (0, 1)),
    help_text      TEXT NOT NULL DEFAULT '',             -- ★ 説明文
    placeholder    TEXT NOT NULL DEFAULT '',             -- ★ 入力例
    settings_json  TEXT NOT NULL DEFAULT '{}',           -- ★ 選択肢・入力制限・表の列定義
    carry_over     INTEGER NOT NULL DEFAULT 0 CHECK (carry_over IN (0, 1)),      -- ★
    show_in_list   INTEGER NOT NULL DEFAULT 0 CHECK (show_in_list IN (0, 1)),    -- ★
    is_searchable  INTEGER NOT NULL DEFAULT 0 CHECK (is_searchable IN (0, 1)),   -- ★
    include_in_csv INTEGER NOT NULL DEFAULT 1 CHECK (include_in_csv IN (0, 1)),  -- ★
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL
);

-- 月次報告（課長の設計＋★の列）
CREATE TABLE report_records (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id       INTEGER NOT NULL REFERENCES users(id),
    department_id INTEGER REFERENCES departments(id),    -- ★ 作成時点の所属課
    period        TEXT NOT NULL,                         -- ★ 対象月 YYYY-MM
    status        TEXT NOT NULL DEFAULT 'draft'          -- ★
                  CHECK (status IN ('draft', 'submitted', 'confirmed')),
    revision      INTEGER NOT NULL DEFAULT 0,            -- ★ 提出後に内容を変更するたびに +1
    submitted_at  TEXT,                                  -- ★
    confirmed_by  INTEGER REFERENCES users(id),          -- ★
    confirmed_at  TEXT,                                  -- ★
    is_legacy     INTEGER NOT NULL DEFAULT 0 CHECK (is_legacy IN (0, 1)),  -- ★ 移行データ
    legacy_report_id INTEGER,                            -- ★ 移行元 reports.id
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
-- ★ 新しく作る報告は 1 人 1 か月 1 件
CREATE UNIQUE INDEX ux_report_records_user_period
    ON report_records (user_id, period) WHERE is_legacy = 0;

-- ★ 報告作成時点の項目定義（過去の報告を当時の定義で表示するため）
CREATE TABLE report_record_fields (
    report_id     INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    field_id      INTEGER NOT NULL REFERENCES report_fields(id),
    label         TEXT NOT NULL,
    field_type    TEXT NOT NULL,
    sort_order    INTEGER NOT NULL,
    is_required   INTEGER NOT NULL,
    settings_json TEXT NOT NULL,
    PRIMARY KEY (report_id, field_id)
);

-- ★ 案件マスタ（客先名・案件名は持たない。客先との対応表はシステムの外で管理）
CREATE TABLE projects (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    code          TEXT NOT NULL UNIQUE,      -- 社内の案件コード
    alias         TEXT NOT NULL DEFAULT '',  -- 客先が特定されない社内向けの呼び名（案件終了後に消去）
    department_id INTEGER REFERENCES departments(id),
    is_active     INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1)),
    ended_on      TEXT,                      -- 終了日（YYYY-MM-DD）
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);

-- ★ 報告の中の案件ブロック（1 報告に複数）
CREATE TABLE report_projects (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    report_id  INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    project_id INTEGER NOT NULL REFERENCES projects(id),
    sort_order INTEGER NOT NULL DEFAULT 0,
    UNIQUE (report_id, project_id)
);

-- 項目ごとの値（課長の設計＋★の列）
CREATE TABLE report_field_values (
    report_id  INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    field_id   INTEGER NOT NULL REFERENCES report_fields(id),
    report_project_id INTEGER NOT NULL DEFAULT 0,  -- ★ 0 = 報告全体の項目 / それ以外 = report_projects.id
    value_text TEXT NOT NULL DEFAULT '',
    updated_at TEXT NOT NULL,
    PRIMARY KEY (report_id, field_id, report_project_id)
);

-- 項目ごとのコメント（課長の設計＋★の列）
CREATE TABLE report_field_comments (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    report_id    INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    field_id     INTEGER REFERENCES report_fields(id),     -- ★ NULL = 報告全体へのコメント
    user_id      INTEGER NOT NULL REFERENCES users(id),
    parent_id    INTEGER REFERENCES report_field_comments(id),  -- ★ 返信先（NULL = 最初のコメント）
    comment_type TEXT NOT NULL DEFAULT 'note'               -- ★ request=追加情報の依頼 / confirm=認識の確認 / note=連絡
                 CHECK (comment_type IN ('request', 'confirm', 'note')),
    thread_status TEXT                                      -- ★ 最初のコメントのみ: open=回答待ち / answered=回答あり / resolved=解決
                 CHECK (thread_status IN ('open', 'answered', 'resolved')),
    resolved_by  INTEGER REFERENCES users(id),              -- ★
    resolved_at  TEXT,                                      -- ★
    comment      TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    updated_at   TEXT NOT NULL
);

-- ★ 課ごとの確認者
CREATE TABLE department_reviewers (
    department_id INTEGER NOT NULL REFERENCES departments(id),
    user_id       INTEGER NOT NULL REFERENCES users(id),
    is_final      INTEGER NOT NULL DEFAULT 0 CHECK (is_final IN (0, 1)),  -- 最終確認者（課長）
    sort_order    INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (department_id, user_id)
);

-- ★ 確認者ごとのチェック（誰がチェック済みか）
CREATE TABLE report_reviews (
    report_id        INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    user_id          INTEGER NOT NULL REFERENCES users(id),
    checked_revision INTEGER NOT NULL,   -- チェックした時点の report_records.revision
    checked_at       TEXT NOT NULL,
    PRIMARY KEY (report_id, user_id)
);
-- 未チェック = 行なし／チェック済 = checked_revision = 現在の revision／更新あり = checked_revision < 現在の revision

-- ★ 提出後の変更履歴（どの項目がどう変わったか）
CREATE TABLE report_value_history (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    report_id  INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    field_id   INTEGER NOT NULL REFERENCES report_fields(id),
    revision   INTEGER NOT NULL,
    old_value  TEXT NOT NULL,
    new_value  TEXT NOT NULL,
    user_id    INTEGER NOT NULL REFERENCES users(id),
    created_at TEXT NOT NULL
);

-- ★ 臨時の依頼（§1.6 型 B）
CREATE TABLE adhoc_requests (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    title         TEXT NOT NULL,
    requester     TEXT NOT NULL DEFAULT '',             -- 依頼元（例: 経営企画）
    purpose       TEXT NOT NULL DEFAULT '',             -- 目的（部下の画面に表示）
    target_type   TEXT NOT NULL CHECK (target_type IN ('all', 'departments', 'users')),
    result_visibility TEXT NOT NULL DEFAULT 'summary'   -- summary=依頼元には集計のみ / detail=個別の回答も可
                  CHECK (result_visibility IN ('summary', 'detail')),
    is_template   INTEGER NOT NULL DEFAULT 0 CHECK (is_template IN (0, 1)),  -- ひな形
    created_by    INTEGER NOT NULL REFERENCES users(id),
    due_at        TEXT,                                 -- 回答期限（ひな形は NULL）
    status        TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('draft', 'open', 'closed')),
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
-- 質問: adhoc_request_fields（月次報告の項目を参照する行 ＝ field_id、または独自の質問 ＝ report_fields と同じ列を持つ）
-- 対象: adhoc_request_targets（課または人）
-- 回答: adhoc_responses（依頼×回答者）／ adhoc_response_values（report_field_values と同じ形式）

-- ★ 更新依頼（§1.6 型 A）
CREATE TABLE report_update_requests (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    report_id    INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    requested_by INTEGER NOT NULL REFERENCES users(id),
    note         TEXT NOT NULL DEFAULT '',
    status       TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'done')),
    created_at   TEXT NOT NULL,
    done_at      TEXT
);

-- ★ 閲覧・出力・管理操作の記録（中身は入れない）
CREATE TABLE access_logs (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER NOT NULL REFERENCES users(id),
    action     TEXT NOT NULL CHECK (action IN ('view', 'export', 'admin')),
    target     TEXT NOT NULL,              -- 例: report:123 / export:period=2026-11,department=2 / field:15
    ip_address TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL
);
-- 「限定」の項目の値は report_field_values.value_text に暗号文で保存する（鍵は DB の外）

-- ★ 状態の履歴（提出・確認完了など）
CREATE TABLE report_status_history (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    report_id  INTEGER NOT NULL REFERENCES report_records(id) ON DELETE CASCADE,
    from_status TEXT,
    to_status  TEXT NOT NULL,
    user_id    INTEGER NOT NULL REFERENCES users(id),
    note       TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL
);
```

- `PRAGMA foreign_keys = ON` を DB 接続のたびに実行する（`config/database.php`）。
- 項目の物理削除を禁止するトリガーは課長の設計を採用する。

## 11. 情報管理（守秘義務）とセキュリティ

月次報告には、**客先の業務内容、案件の期間、客先の人員計画（増員・減員）** など、客先との秘密保持契約（守秘義務）の対象になりうる情報が集まる。集めること自体はよいが、次を前提として設計・運用する。

> この章は設計上の対策の案であり、法的な判断ではない。何を記録してよいかは、客先との契約内容に従って会社（総務・法務の担当など）が判断する。

**漏えいは起きる前提で設計する（§1.4）。** 対策は「防ぐ」だけでなく、「漏れても読めない・結び付かない・残っていない・範囲を特定できる」の 4 つを重ねる。

### 11.0 漏えいしたときの影響（設計の目標）

| 漏えいの形 | 現行（main） | 見直し後の目標 |
|---|---|---|
| DB ファイルだけが漏れる（2026-11-12 時点で実際に起きうる） | 全ユーザーのメールアドレス、パスワードのハッシュ、報告の全文が読める | 案件はコードだけで客先が分からない。限定の項目は暗号化されて読めない。古い自由記述は消えている |
| ユーザー 1 人のアカウントが乗っ取られる | その人の閲覧範囲の報告がすべて見える | 同じだが、閲覧の記録から「何が見られたか」を特定できる |
| 出力した CSV が流出する | — | 限定の項目は出力されない。ファイルに出力者・日時が入っており、出どころが分かる |
| サーバーごと乗っ取られる | すべて漏れる | 鍵も取られうるが、客先との対応表はシステムの外にあるので、客先は特定されない |

### 11.1 客先名・案件名をシステムに入れない

| 対策 | 内容 |
|---|---|
| 案件コード | 報告では、社内で付けた**案件コード**（例: `P-0012`）を選ぶ。客先名・案件名は報告に記録しない |
| 案件マスタ | 案件コードと、客先が特定されない**社内向けの呼び名**（例: 「物流系・在庫管理更改」）だけを持つ。**客先名との対応表はこのシステムに入れず**、課長の手元など社内の別の場所で管理する |
| 自由記述の注意 | 自由記述の項目には「客先名・固有名詞・個人名を書かない」旨を説明文に表示する |
| 業務システムの種類 | 「在庫管理」などの分類までにとどめ、客先固有のシステム名は書かない |

### 11.2 項目ごとの機密区分

項目マスタに**機密区分**を持たせ、見られる人と出力先を制限する。

| 区分 | 閲覧できる人 | CSV 出力 | 例 |
|---|---|---|---|
| 通常 | 本人・確認者・管理者 | ○ | 作業フェーズ、進捗 |
| 社外秘 | 本人・確認者・管理者 | ○（出力ファイルに「社外秘」と表示） | 担当内容、問題・悩み事 |
| 限定 | 本人・最終確認者（課長）・管理者 | ×（管理者のみ可） | 人員の動きの詳細、客先の追加要員の募集 |

- 画面と出力ファイルに機密区分を表示する。
- **「限定」の項目は暗号化して保存する**（PHP の標準機能 sodium または openssl。鍵は公開ディレクトリと DB の外のファイルに置く）。DB ファイルだけが漏れても読めない。
  - 暗号化した項目は検索できない。検索が必要な項目は「限定」にしない。
  - 鍵をなくすとデータを読めなくなるため、鍵の保管・バックアップの手順を決める。

### 11.2.1 閲覧・出力の記録

| 記録するもの | 内容 |
|---|---|
| 閲覧 | 誰が・いつ・どの報告を開いたか |
| 出力 | 誰が・いつ・どの条件で CSV を出力したか |
| 管理操作 | 項目マスタ・案件マスタ・ユーザー・権限の変更 |

- 漏えいが疑われるときに、影響を受けた報告・案件を絞り込むために使う。
- 記録自体には報告の中身を入れない（記録が漏れても中身は分からない）。
- CSV には出力者と出力日時を入れる。

### 11.3 稼働環境の前提条件（実データを入れる前に必須）

本番予定のサーバーは**インターネットに公開されたレンタルサーバー**である。2026-11-12 時点で、**DB ファイルがログインなしでダウンロードできる状態**（`dev_check_report` の監査結果）。この状態で客先に関わる情報を集めると、そのまま漏えいにつながる（2026-11-12 時点の DB はテストデータのみ）。

実データを入れる前に、少なくとも次を済ませる。

| No | 対策 |
|---|---|
| 1 | DB を Web から取得できない配置にする（`data/` を公開ディレクトリの外へ、または `.htaccess` で拒否）。対策後に監査ツールで確認する |
| 2 | HTTPS を強制する。Cookie に Secure・HttpOnly・SameSite を付ける |
| 3 | テストユーザー（共通パスワード）を削除する |
| 4 | ログインを強くする（§11.3.1）。社員の大半は客先に常駐しているため、**接続元の IP アドレスでは制限できない** |
| 5 | パスワードの強さの基準、ログインの試行回数の制限 |
| 6 | DB のバックアップの保管場所と、バックアップ自体の守り方 |

### 11.3.1 社外から使う前提の対策

社員の大半は客先に常駐しており、社内のネットワークからは使えない。**インターネットのどこからでも使える前提**で、接続元の制限の代わりに次を重ねる。

| 対策 | 内容 |
|---|---|
| 2 段階認証 | パスワードに加えて、スマートフォンの認証アプリ（TOTP。Google Authenticator 等）の 6 桁のコードを入れる。PHP の標準機能だけで実装できる。初回の設定以外は、ログインのたびにコードを入れるだけ |
| ログインの試行制限 | 一定回数失敗したら、そのアカウントを一定時間ロックする |
| 自動ログアウト | 一定時間操作がなければログアウトする |
| 画面を端末に残さない | ブラウザーのキャッシュに残さない設定（`Cache-Control: no-store`）。ログアウトで画面の内容が戻るボタンで見えないようにする |
| スマートフォンで使える画面 | 客先の PC を使わずに、自分のスマートフォンで入力できるようにする（F-15） |

**運用で決めること**

- **客先の PC・客先のネットワークから使わない**よう案内する。客先の端末から社内の情報を入力・閲覧すること自体が、客先のセキュリティ規程や契約に触れるおそれがあり、客先の端末に履歴が残る。
- **私物のスマートフォンで使う前提とする**。
- 2 段階認証の設定を忘れた・機種変更したときの再設定の手順（管理者が初期化する）。

**私物のスマートフォンで使うための対策**

| 対策 | 内容 |
|---|---|
| スマートフォン優先の画面 | 入力・確認・コメントの返信をスマートフォンだけで完結できるようにする。PC は管理・集計用 |
| 端末に何も残さない | アプリのインストールなし（ブラウザーだけ）。画面をキャッシュさせず、端末にデータを保存しない |
| スマートフォンでは出力しない | CSV 出力は PC の画面からだけにし、スマートフォンにファイルを残さない |
| 紛失・機種変更 | 本人または管理者が「すべての端末からログアウト」と 2 段階認証の初期化をできるようにする |
| 画面ロックの案内 | スマートフォンの画面ロックを設定するよう利用時に案内する |

2 段階認証はログインのたびにひと手間増えるため、§1.3（部下の作業を増やさない）と両立するよう、「この端末を記憶する」などの負担を減らす工夫を入れる。利用は月 1 回なので、記憶の期間は 1 か月より長くする（例: 90 日。§1.5）。

| 月 1 回の利用で困ること | 対策 |
|---|---|
| パスワードを忘れた | ログイン ID ＋ 2 段階認証のコードで本人確認し、自分で再設定する |
| スマートフォンを機種変更して 2 段階認証のコードが出ない | 最初の設定時に発行する予備のコード（数個、1 回ずつ使える）で入り、設定し直す。予備のコードもない場合は管理者が初期化する |

### 11.4 保管期限

- **自由記述は短い期間（例: 確認完了から 12 か月）で消す。** 集計に使う選択式の値（フェーズ、進捗、継続見込み等）は残す。
- 報告そのものは**一定期間（例: 3 年）を過ぎたら削除**する。期間は会社で決める。
- 案件が終わったら、案件マスタの社内向けの呼び名も消し、コードだけ残す（過去の集計は残す）。
- 消す処理はバックアップにも及ぶようにする（古いバックアップを保管期限で消す）。

### 11.4.1 漏えい時の対応手順

設計とあわせて、漏えいが起きたときの手順書を用意する。

1. サイトを止める（またはログインを止める）
2. 閲覧・出力の記録から、影響を受けた報告・案件・ユーザーを特定する
3. 案件コードから、社内の対応表で影響を受けた客先を特定する（システムの外で行う）
4. パスワードの変更、鍵の入れ替え
5. 会社の手順に従って報告・連絡する

### 11.4.2 個人情報も減らす

- ログイン ID にメールアドレスを使わない（現行はメールアドレス）。社内の ID にする。
- 報告の画面・出力では、氏名でなく社員番号や表示名を選べるようにする。

### 11.5 運用で決めること（会社への確認事項）

| No | 内容 |
|---|---|
| 1 | 客先との契約上、案件の期間・人員計画などを社内システムに記録してよいか |
| 2 | 報告を閲覧できる範囲（課の中だけか、部長・役員まで見るか） |
| 3 | 社外のサーバー（さくらのレンタルサーバー）に置いてよいか。社員の大半が社外から使うため、インターネットから接続できる場所に置く必要はある |
| 3-2 | 客先の PC・ネットワークから使わない運用でよいか（私物のスマートフォンで使う前提） |
| 4 | 保管期限 |

### 11.7 資料用の出力

課から外に出る資料は課長が作る。システムは、その**元ネタを報告に使いやすい形で出す**。

| 形式 | 作り方 | 向いている使い方 | 備考 |
|---|---|---|---|
| **印刷用画面 → PDF** | 印刷向けに整えた画面を出し、ブラウザーの「PDF として保存」で保存する | そのまま上に見せる・添付する | ライブラリ不要。日本語のフォントはブラウザーが処理する。Ubuntu・Windows・スマートフォンのどれでも保存できる |
| **Excel 形式（.xlsx）** | PHP で xlsx を組み立てる（xlsx は XML を zip にまとめたもの） | 課長が表を加工して資料を作る | Excel でも、Ubuntu の LibreOffice Calc でも開ける |
| CSV | UTF-8（BOM 付き） | ほかのツールに取り込む | 書式なし |

- **ODF（.ods / .odt）について**: Ubuntu では LibreOffice が標準で入っており、ODF をそのまま扱える。ただし LibreOffice は xlsx も開けて保存できるため、資料の受け手（Windows の Excel が多いと想定）に合わせて **xlsx を基本にする**。ODF が必要なら、xlsx と同じ仕組み（XML を zip にまとめる）で追加できる。
- **PDF をサーバーで直接作らない理由**: 日本語のフォントを埋め込む PDF を作るにはライブラリが必要で、稼働条件（Composer を使わない）に合わない。印刷用画面からの保存で十分な見た目にできる。
- xlsx を作るのに PHP の zip 機能（ZipArchive）を使う。本番のサーバーで使えるか確認する（Q-16）。使えない場合は、zip を自前で組み立てる。

**出力するファイルの守り方**（§1.4）

- 出力は**課長（と管理者）だけ**、**PC の画面からだけ**（§11.3.1）。
- ファイルと印刷用画面の上部に「社外秘」「出力者」「出力日時」を入れる。
- 「限定」の項目は出力しない（管理者のみ例外）。臨時の調査で「集計のみ」にした依頼は、集計だけを出力する。
- 出力したことを記録する（§11.2.1）。

### 11.6 アプリのセキュリティ

`dev_check_report` の監査で見つかった問題を、作り直しの中で解消する。

- CSRF 対策を全 POST に適用（共通関数にする）
- 未ログイン時の転送先を、呼び出し元の階層に依存しない URL にする
- `PRAGMA foreign_keys = ON`
- 画面に出す値はすべて `h()`。項目マスタの表示名・説明文・選択肢も同様（HTML は書けない）
- 入力チェックはサーバー側で項目マスタの設定に従って行う
- `public/setup.php`、`setup_admin.php` は公開しない
- DB を Web から取得できない配置にする（`data/` を公開ディレクトリの外へ、または `.htaccess`）
