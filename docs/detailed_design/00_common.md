## 2. URL の決まり

| 決まり | 内容 |
|---|---|
| 画面 | GET で開く。画面を開くだけでデータは変えない |
| 更新 | POST だけで受ける。処理のあとは結果の画面へ転送する（PRG） |
| ID の受け取り | `input_id()` で受け、1 以上の整数（10 桁まで）の文字列でなければ 400 |
| 文字列の受け取り | GET は `get_str()`、POST は `post_str()` で受ける。配列など文字列でない値・UTF-8 として正しくない値は 400。スーパーグローバル変数（`$_GET`・`$_POST`・`$_COOKIE`）を `(string)`・`(int)` などで直に変えない・関数に直に渡さない（配列で送られると 500 になる・黙って別の値になるため）。配列で受ける欄は `is_array()`、その中の値は `is_string()` で確かめてから使う。`$_REQUEST` は使わない。自動検証の「スーパーグローバル変数を型を確かめて読む」（`tools/test/check_superglobals.py`）と「GET の項目に配列を送っても 500 にしない」（`smoke_get_arrays.py`）で見る。Filter 関数（`filter_input()` など）は使わず、用途ごとの形（正規表現・許す値の一覧）で確かめる（監査で承認済み。2026-11-26） |
| 対象月 | `YYYY-MM`。正規表現 `\A\d{4}-(0[1-9]|1[0-2])\z` で確かめる |
| 正規表現 | 入力の確かめは、文字列全体の先頭・末尾の `\A`・`\z` で囲む（`^`・`$` は使わない。`$` は末尾の改行の前にも合うため、改行を混ぜた値が確かめを抜けるおそれがある）。自動検証の「正規表現は文字列全体で確かめる」で見る |
| 転送先 | 自分のサイトの中のパスだけ（`/` で始まり、`//` で始まらず、`\` と制御文字を含まない）。それ以外は `/index.php` にする。転送は 303 |
| 未ログイン | どの階層の画面からでも、`/report-system/login.php?next=<元の画面>` へ転送する（`next` は `base_path` を除いた自サイトのパスだけ受け付ける。POST のときと、`/login.php` で始まるものは付けない） |

## 3. すべての要求で行う共通処理

基本設計書 §15.1。`bootstrap.php` は設定の読み込み、時刻帯・文字コードの設定、共通の処理の読み込み、エラーの扱いの設定（画面に詳細を出さない）だけを行う。失敗したときは 500「ただいま利用できません」。

エラーの記録（`app_init_error_handling()`）: 警告は例外にし、受け止められなかった例外は `app.log` に ERROR として残して 500 を返す。時間切れ（`max_execution_time`）・メモリ不足などの致命的なエラーは例外の受け口を通らないので、終わるときに拾って `ERROR fatal: <内容> at <ファイル>:<行> path=<画面のパス>` を残す（問い合わせの部分は質問の文などが入るので残さない）。配布の一式の「記録を書き出す」は、この ERROR・WARN の行を書き出す。

各画面の処理は、最初に `page_start()`（`session.php`）を呼ぶ。`page_start()` は次を順に行う。

| 順 | 処理 | 失敗したとき |
|---|---|---|
| 1 | 共通のヘッダーを付ける（§4） | — |
| 2 | セッションの開始。サイトの印の確認（§5） | 新しいセッション |
| 3 | DB に接続し、`PRAGMA foreign_keys = ON`、`PRAGMA busy_timeout = 5000`、`PRAGMA journal_mode = WAL` | 503 |
| 4 | ログイン不要の画面（ログイン・再設定）は、POST なら CSRF の確認をしてここで終わる | 403 |
| 5 | ログインの確認。自動ログアウト（操作がない時間・最長の時間）、`is_active`、`session_version` の確認（§5） | ログイン画面へ |
| 6 | 2 段階認証が未設定の段階（`setup`）なら、G-16 の設定だけ使える | G-16 の 2 段階認証へ |
| 7 | パスワードの変更が必要な人（`must_change_password = 1`）は、G-16 のパスワード変更だけ使える | G-16 のパスワードへ |
| 8 | POST なら CSRF の確認（§6） | 403 |

`page_start()` のあとに、画面ごとの処理で次を行う。

| 順 | 処理 | 失敗したとき |
|---|---|---|
| 9 | 画面ごとの権限の確認（§10） | 403 |
| 10 | POST なら送信の番号の確認（§7） | 1 回目の結果を返す／処理中の案内 |
| 11 | 画面ごとの処理（入力の確認 → 状態の確認 → 1 つのトランザクションで更新 → 記録） | 入力エラーは同じ画面に戻す |

- パスワードだけ済んで 2 段階認証のコードを待っている間は、セッションに `pw_uid` と `pw_at` だけを持つ（`pw_stage_minutes` 分だけ有効）。ログインの状態ではないため、ほかの画面を開くとログイン画面へ戻る。
- 稼働の確認（`health.php`）は `page_start()` を通らない（§14）。

## 4. 共通のヘッダー

| ヘッダー | 値 | 目的 |
|---|---|---|
| `Cache-Control` | `no-store` | 画面の内容を端末に残さない |
| `Pragma` | `no-cache` | 同上（古いブラウザー向け） |
| `X-Frame-Options` | `DENY` | 他のサイトへの埋め込みを防ぐ |
| `X-Content-Type-Options` | `nosniff` | |
| `Referrer-Policy` | `same-origin` | |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; form-action 'self'; frame-ancestors 'none'; base-uri 'none'` | 外部の読み込みと埋め込みのスクリプトを禁止する |

`Strict-Transport-Security` はまだ付けていない。本番で HTTPS の動作を確認してから付ける。

公開ディレクトリの `.htaccess` では次を行う。

- HTTP で来た要求を HTTPS へ転送する（301）。さくらのレンタルサーバーは SSL をプロキシで終えるため、`HTTPS` が off で、かつ `X-Sakura-Forwarded-For` が空のときだけ転送する。
- ファイルの一覧を出さない（`Options -Indexes`）。
- `_boot.php` を直接開かせない。
- 送るファイルは、システムが送る `.php`・`.css`・`.js`（小文字）だけにする（許すものだけを書く形。`mod_rewrite` で、置かれているファイルのうち、ほかの拡張子・拡張子のないもの・大文字の `.PHP` などを 403 にする）。フォルダー（`index.php` への切り替え）と無いもの（404）はそのまま。`.well-known/` は除く。
- 二重の守りとして、DB・鍵・証明書・控え・ソース・事務の文書・圧縮ファイル（形式を問わない。`.css.br`・`.js.gz` などの事前圧縮も）・名前が `~` で終わるものの拡張子を、大文字・小文字を区別せずに拒否する（`mod_rewrite` が効かないときの備え。一覧は `.htaccess` と `公開範囲.txt`）。
- 手元の検証（PHP の組み込みサーバー）は `.htaccess` を読まないので、`.htaccess` を変えたら、反映のあとにサーバーで確かめる（`公開範囲.txt` の「反映のあとに確かめること」）。

## 5. セッションと自動ログアウト

| 項目 | 値 |
|---|---|
| Cookie | 名前は `mr_session`（端末の記憶は `mr_device`）。`HttpOnly`、`SameSite=Lax`。`Secure` は設定 `https` に従う。パスは `base_path` ＋ `/`（`base_path` が空なら `/`）。`session.use_strict_mode` と `use_only_cookies` を有効にする |
| 置き場所 | `session_dir`（既定 `app/data/sessions`。なければ 0700 で作る）。PHP の既定の場所は、同じサーバーの別のサイトと共通のことがあるので使わない。作れない・書けないときは、`app.log` に WARN を残して PHP の既定の場所で続ける。古いものは PHP の掃除で消す（`gc_maxlifetime` = `session_max_hours`） |
| サイトの印 | セッションの `site` に、暗号化の鍵と、`app/` の場所・`base_path`・`db_path` から作った値（HMAC-SHA256）を入れ、`session_boot()` で比べる。違う・無いときは、そのセッションの中身は変えずに手放し、新しいセッションにする（ログイン済み・コード待ち・設定待ちのどれも引き継がない。元のサイトのログインは切れない）。デモ用と本番のように同じサーバーにあるサイトの間で、ログインを流用させないため |
| ID の作り直し | パスワードが合ったとき、ログインの完了時（2 段階認証が未設定の `setup` の段階を含む）、2 段階認証の設定の完了時、パスワード変更時に `session_regenerate_id(true)` |
| 操作がないときのログアウト | 30 分。「一定時間操作がなかったため、ログアウトしました。」と出す |
| ログインの最長 | 12 時間。同上 |
| 利用者の状態 | `is_active = 0` になった人はログアウトさせる |
| すべての端末からログアウト | `users.session_version` を 1 増やし、記憶した端末もすべて消す。セッションに持つ版と違えばログアウトさせる。2 段階認証の設定とパスワードの変更・再設定でも版を上げる |
| ログアウト | POST だけで受ける。セッションを破棄し、Cookie を消す。端末の記憶は残す（G-16 で消せる） |

---

## 6. CSRF

- セッションごとに 32 バイトの乱数のトークン（16 進 64 文字）を作り、すべてのフォームに隠し項目 `csrf_token` で入れる。
- POST を受けたら `hash_equals()` で比べる。違えば 403「画面を開き直してから、もう一度お試しください」。ログイン不要の画面（ログイン・再設定）でも確かめる。
- 自動保存などの JavaScript からの送信も、同じトークンをフォームの値として付ける（ヘッダー `X-CSRF-Token` でも受け付ける）。

## 7. 送信の番号（二重登録の防止）

基本設計書 §15.3。

| 項目 | 内容 |
|---|---|
| 番号の作成 | 画面を作るときに、更新のフォームごとに 16 バイトの乱数（16 進 32 文字）を隠し項目 `request_key` で入れる（`form_hidden()`）。形が違えば 400 |
| やり直し | 番号は隠し項目のため、同じ画面から送り直せば同じ番号になる。自動保存は送るたびに JavaScript が新しい番号を作る |
| サーバーの処理 | `request_keys` に番号を登録してから処理する。登録済みで `done` なら、処理せずに「前の送信で処理済みです。」と出して 1 回目の結果（転送先）へ移す。`processing` なら 409「前の送信をまだ処理しています。しばらく待ってから画面を読み直してください。」 |
| 別の人・別の操作 | 同じ番号でも利用者か操作が違えば 400 |
| 入力エラー | 控えを消し（`rk_cancel()`）、直して送り直せば処理する。409 以外のエラーの画面を出すときも、処理中の控えを消す |
| 控えの期間 | 1 日。それより古いものは、1 日 1 回の後片付け（ログイン画面を開いたとき）で消す |

## 8. 暗号化

基本設計書 §8.1、§11.1。

### 8.1 対象

| 対象 | 暗号化する |
|---|---|
| 自由記述の値（`single_text`、`multi_text`、`table`。`table` は列の種類を問わず全体） | 常に |
| 機密区分が「限定」の項目の値（種類を問わない） | 常に |
| コメントの本文 | 常に |
| 変更履歴の変更前・変更後（対象の項目が暗号化の対象なら） | 常に |
| 臨時の調査の回答（上と同じ決まり） | 常に |
| 2 段階認証の秘密の値 | 常に |
| 選択式の値、数値、日付、年月、案件コード（通常・社外秘） | しない |

### 8.2 方式

| 項目 | 内容 |
|---|---|
| 方式 | AES-256-GCM（PHP の OpenSSL 機能。PHP 7.4 で使える） |
| 鍵 | 32 バイトの乱数。`keys/field_<版>.key`（はじめは `field_v1.key`。入れ替えるごとに `v2`・`v3`）に Base64 で保存（権限 600）。DB・公開ディレクトリとは別の場所。`app/bin/migrate.php` が、なければ作る |
| 保存の形 | `v1:` ＋ Base64（IV 12 バイト ＋ 認証タグ 16 バイト ＋ 暗号文）。`v1` は鍵の版 |
| 付加データ | テーブル名と行の識別（例: `rfv:<report_id>:<field_id>:<block>`）を付加データにする。暗号文を別の行に移し替えても復号できない。一覧は DB 編 §4 |
| 鍵の版 | 暗号化は `app_state.crypto_version`（なければ `v1`）の鍵で行い、復号は暗号文の先頭の版の鍵で行う |
| 鍵の入れ替え | `php app/bin/rotate_key.php`（§8.2.1） |
| 復号の失敗 | 画面には「この内容は表示できません」と出し、ログに記録する |

### 8.2.1 鍵の入れ替え（rotate_key.php）

- `php app/bin/rotate_key.php [--dry-run] [--db=<DB>]`。メンテナンス中だけ動く（`--dry-run` はいつでもよい）。`--db` は別の DB（写し）で試すとき。新しい鍵は同じ `key_dir` に作る。
- 確かめ（1 つでも合わなければ何も変えない）: DB と表があること、名前が `_enc` で終わる列がすべて対象の一覧（`rotate_key_targets()`）にあること、全件を復号できること（できないものは表・列と件数だけを出す）。
- 控え `app/backups/before_key_rotation_<日時>_<乱数>.sqlite` を取り、次の版（`v2` など）の鍵を作る。1 つのトランザクションで、全件を新しい鍵で暗号化し直し（1 件ずつ復号して元と同じことを確かめる）、古い版が残っていないことを確かめ、`app_state.crypto_version` と記録 `admin key:rotate;v1->v2;count=…` を書く。失敗したら DB は元のまま（新しい鍵のファイルは残り、次に流したときに使う）。
- 終わったら全件を読み直し、`VACUUM` とチェックポイントで古い暗号文を DB のファイルから消す。
- 古い鍵は消さない（前のバックアップと控えを読むのに要る）。`www` の外に移しても動く。`migrate.php` は今の版の鍵だけを作る。
- サイトの印（§5）に鍵を使うので、入れ替えると全員がログインし直しになる。
- 守れるのは、入れ替えのあとのデータだけ。抜かれた DB と古い鍵の組は読める。2 段階認証の秘密の値は暗号化し直すだけで値は変わらないので、抜かれたおそれがあるときは、全員の総入れ替え（G-14 §6.11）も行う。
- 検証は `tools/test/smoke_key_rotation.py`。

### 8.3 検索

自由記述は DB では検索できないため、検索の条件（対象月・課・選択式の値）で絞った報告を、見る権限のある範囲だけ復号して、アプリの中で文字列を探す。1 回の検索で復号する報告の上限は `search_decrypt_limit`（既定 2,000 件）で、超えるときは条件を足すよう案内する。探す項目は項目マスタの `is_searchable` で決める。画面と処理は G20_search.md。

## 9. 入力の確認

### 9.1 3 段階（基本設計書 §15.2）

| 段階 | 場所 | 内容 |
|---|---|---|
| 1 | 画面 | HTML の `required`、`maxlength`、`type`、`min`/`max`。補助であり、頼らない |
| 2 | サーバー | 項目マスタの設定に従い、すべてを確認し直す（§9.2） |
| 3 | サーバー（DB を見る） | 重複、存在、状態（例: 確認完了の報告は変更できない） |

### 9.2 入力部品ごとの確認

| 種類 | 確認 | 保存の形 |
|---|---|---|
| `single_text` | 改行なし。制御文字なし。UTF-8 として正しい。最大文字数（設定。既定 200 文字） | 文字列（暗号化） |
| `multi_text` | 制御文字は改行・タブのみ可。改行は LF にそろえる。最大文字数（設定。既定 2,000 文字） | 文字列（暗号化） |
| `date` | `YYYY-MM-DD` で、実在する日付 | 文字列 |
| `month` | `YYYY-MM` | 文字列 |
| `number` | 整数部 12 桁まで、負の数も可。最小・最大・小数の桁数（設定） | 数字の文字列 |
| `select`・`radio` | 選択肢のコードのどれか（有効なもの。無効にした選択肢も、保存済みの値から変えていなければ受け付ける） | 選択肢のコード |
| `checkbox` | `0`・`1`・空 | `1`／空 |
| `multi_check` | 選択肢のコードの集合。重複なし（無効の選択肢の扱いは `select` と同じ） | JSON の配列 |
| `table` | 行数の上限（設定 `max_rows`。既定 20 行）。すべて空の行は捨てる。各セルは制御文字なし（改行は `multi_text` の列だけ可）、2,000 文字以内だけを確かめる（数値・日付・選択肢の確認はしない）。列の種類は `single_text`・`multi_text`・`number`・`date`・`select` | JSON の配列（全体を暗号化） |

- 文字数は `mb_strlen()` で数える（`mbstring` がない環境では `preg_match_all('/./us')` で数える）。
- 前後の空白は取り除いてから確認する。
- 空の値は空の文字列で保存する（`multi_check` で何も選ばないときも空）。
- 必須の確認は「提出」のときだけ行う。下書きの保存では行わない。

### 9.3 客先名らしい言葉の注意

- 自由記述の値に、`warning_words` の言葉が含まれるかを、画面（入力中）とサーバー（保存時）の両方で調べる。
- 含まれても保存は止めない。サーバーは、含まれた自由記述の欄を `report_field_values.has_warning = 1` にする（確認者の画面の印に使う）。
- 調べるときは、全角・半角と大文字・小文字をそろえてから比べる（サーバーは `mb_convert_kana('asKV')` のあと小文字に、画面は全角英数字・全角空白を半角にしてから小文字にする）。
- 欄の下に「客先名や個人名が含まれていませんか」と出す。
- 初期の言葉は 14 個（`株式会社`、`(株)`、`㈱`、`有限会社`、`様`、`御中`、`Inc.`、`Ltd.` など）。`schema_ensure()` が登録する。

## 10. 権限の判定

`perm.php` にまとめ、画面ごとの処理は必ずここを通す。

### 10.1 役割の判定

| 役割 | 判定 |
|---|---|
| 管理者 | `users.is_admin = 1`（`is_admin()`） |
| システム管理者補佐 | `users.is_admin_deputy = 1`（`is_admin_deputy()`）。管理の画面は `can_manage_system()`（管理者か補佐）・`require_system_manager()` で開ける。個々の情報を出す所は、画面ごとに `is_admin()` で分ける（G-14 §6.9） |
| 課長（その課の最終確認者） | `department_reviewers` に `(課, 本人, is_final = 1)` がある |
| 確認者（その課） | `department_reviewers` に `(課, 本人)` がある（課長を含む） |
| 課別項目の管理者 | `department_admins` に `(課, 本人)` がある、その課の課長、または管理者・補佐 |
| 部下 | 上のどれでもない、ログインしている利用者 |

役割は課ごとに決まる。同じ人が、ある課の確認者で、別の課では部下ということもありうる。

**補佐（開発担当）の保護（K-075）**: システム管理者は、補佐（開発担当）と、前に開発担当だった人のアカウントに入れない（パスワード・2 段階認証の初期化、予備のコードの確認、復旧コードの発行、1 人での再初期化は 403。`security_is_protected()`）。復旧は、管理者の申請と別の補佐の承認の 2 人で行う（G-14 §6.11）。

### 10.2 報告を見られるか

**専門職（技師・担当課長・担当部長。K-074）**: 次の決まりを、報告（`reviewer_can_see_report()`）・出力・横並び・検索・課の調査の回答・目標管理のすべてに当てる。判定は `specialist_viewable_as()`。

| 見る人 | 技師 | 担当課長 | 担当部長 |
|---|---|---|---|
| 一般・主任（確認者） | × | × | × |
| 課長代理（確認者） | × | × | × |
| 課長（最終確認者） | ○ | ○ | × |
| 専門職どうし | × | × | × |

専門職は、確認者の設定が残っていても、ほかの人の報告を見られない（`report_view_grants()` が空）。担当部長の報告は本人だけが見られ、確認の完了・課の調査の対象にもならない。


```text
削除済みの報告                     → だれも見られない（404）
本人の報告                         → 見られる
下書き                             → 本人だけ
報告の課（作成時の課）の確認者      → 見られる（ただし「限定」の項目は課長だけ）
報告の課を引き継いだ課の確認者      → 見られる（同上。組織の改訂。G-14 §6.6）
本人の今の課の確認者                → 見られる（同上。報告は人について回る。課を移った人の移る前の報告）
「ラインごと」の課で担当のラインがある確認者 → 本人の今のラインがそのラインのときだけ（課長はラインに関係なく見る。G-14 §6.7）
それ以外（管理者を含む）            → 見られない（存在しない報告と同じ 404 を返す）
```

判定は `reviewer_can_see_report()`（`perm.php`）。確認者の設定 1 行ごとに「その課と、引き継いだ前の課」「課長か」「担当のライン」を持ち（`report_view_grants()`）、報告の課か本人の今の課（`user_current_placement()`）に当たるかを見る。

「チェック n/m」の m（チェックを求める確認者）は、報告を作ったときの課（と引き継いだ課）の有効な確認者のうち、その報告を見られる人（`report_expected_reviewer_ids()`。ラインごとの課では担当のラインの確認者と、課全体の確認者・課長）。チェックの操作もこの人たちだけができる。課を移った人の移る前の報告を新しい課の確認者が見られても、チェックは求めない。

管理の権限と、報告を見る権限は分ける（基本設計書 §8）。管理者でも、確認者でない課の報告の中身は見られない（`can_view_report()`・`can_view_restricted()` は管理者を特別に扱わない）。中身を出す画面の課の一覧は `reviewable_departments()`（確認者の課だけ）、課長の画面は `final_departments()`（課長の課だけ）。提出状況（G-08）だけは `status_departments()` で、管理者は全課を見られる（中身は出さず、報告へのリンクも出さない）。

### 10.3 機密区分による表示

| 区分 | 本人 | 確認者 | 課長 | 管理者（確認者でない課） |
|---|---|---|---|---|
| 通常・社外秘 | ○ | ○ | ○ | × |
| 限定 | ○ | 「（限定のため表示しません）」 | ○ | × |

## 11. メッセージと画面の共通部品

### 11.1 メッセージの出し方

| 種類 | 出し方 |
|---|---|
| 成功 | 本文の上に出す（自動では消えない） |
| 入力エラー | 本文の上にまとめて出し、該当する欄の下にも出す。消えない |
| 注意（客先名らしい言葉など） | 該当する欄の下に黄色で出す |
| エラー（権限・障害） | 専用の画面。英語や内部の情報は出さない |

文言は `msg('既定の文言', [差し込み])` で出し、課長が G-17 で変えられる（G-01・G-02 の文言は固定）。JavaScript の文言は `M()`。仕組みは G17_messages.md §4。

### 11.1.1 提出のお知らせ（2026-11-18。仮設定 K-061）

メールは使わない。ログインしたあとのすべての画面（報告の作成・編集の画面 G-04 を除く）で、本文の上に黄色の札で出す（`app/lib/reminder.php` の `reminder_banner_list()`。`render()` が `layout.php` に渡す）。札を押すと、その月の報告の作成・編集の画面へ行く。印刷には出さない。

| 知らせ | 出す条件 | 文言 |
|---|---|---|
| 締め日が近い | 課に締め日があり、今の対象の月（`report_target_period()`）を提出していない。締め日まで 0〜3 日（`REMINDER_CLOSE_SOON_DAYS`） | 「{月}の報告の締め日は {日付} です（あと {N} 日）。まだ提出していません。」、当日は「{月}の報告の締め日は今日（{日付}）です。まだ提出していません。」 |
| 締め日を過ぎた | 1 つ前の月（対象の月は締め日を過ぎると次の月に切り替わるため）を提出しておらず、その締め日を過ぎ、まだ作成・編集できる月。その月が終わってから作られたアカウントには出さない | 「{月}の報告の締め日（{日付}）を過ぎています。まだ提出していません。」 |
| 促された | 課長・確認者が G-08 で促した（§6.3）。当月と過去 3 か月の分で、その月を提出するまで | 「{促した人} さんから、{月}の報告を提出するよう知らせが届いています（{日付}）。」 |

### 11.2 共通のエラー画面

| 状態 | 文言 |
|---|---|
| 400 | 要求の内容が正しくありません。画面を開き直してください |
| 403 | この操作を行う権限がありません |
| 403（CSRF） | 画面を開き直してから、もう一度お試しください |
| 404 | 対象のデータが見つかりません |
| 409 | 前の送信をまだ処理しています。しばらく待ってから画面を読み直してください |
| 500・503 | ただいま利用できません。時間をおいてもう一度お試しください |

- 文言の終わりには「。」を付ける。画面ごとに別の文言を出すこともある（例: 「出力は PC から行ってください。」）。
- エラーの画面にはメニューを出さず、「ホームへ戻る」のリンクだけを出す。

### 11.3 通信が切れたとき（JavaScript）

| 状況 | 動き |
|---|---|
| 保存・提出 | 送る前にログインの状態を確かめ（§11.3.1）、通常のフォームの送信をする。押したあと 30 秒は、同じフォームを二重に送らせない |
| 送り直し | 送信の番号は隠し項目のため、同じ画面から送り直せば同じ番号になる（二重には登録されない） |
| 自動保存 | 入力が変わったときだけ 60 秒ごとに送る。30 秒応答がないか通信のエラーなら「通信が切れたため自動保存できませんでした。入力は残っています」と出す。ログイン切れ・エラー（404・500 など）は、それぞれの文で出す（G-04 §7）。送り先は `form.getAttribute('action')` で読む（`name="action"` のボタンがあると `form.action` はボタンを指す） |

### 11.3.1 ログインが切れたとき（JavaScript）

POST のフォーム（ログアウト・別のタブで開くものを除く）は、送る直前に `GET /session_check.php` でログインの状態を確かめる。

| 結果 | 動き |
|---|---|
| ログイン中で、画面を開いた人と同じ | 画面の CSRF トークンを今のものにして、同じボタンで送る（確認の表示は 1 回だけ） |
| 切れている（401） | 送らずに知らせ、別のタブのログインのボタンを出す。入力は画面に残る。ログインし直して押せば送る |
| 別の利用者でログインしている | 送らずに知らせる |
| 通信できない・10 秒応答がない | 送らずに知らせる |
| 確かめられない（503 など） | そのまま送り、サーバーに任せる |

- `session_check.php` は `{"ok":true,"user_id":…,"csrf_token":…}` を返す（同じサイトからの読み取りだけ。CORS の見出しは出さない）。呼ぶと最後の操作の時刻が新しくなる。
- JavaScript が動かないときなど、切れたまま届いた POST は保存せず、ログイン画面で「送信した内容は保存されていません」と知らせる。
- 端末には入力を保存しない（基本設計書 §4.4）。

### 11.4 確認の表示

ブラウザーの標準の確認（`window.confirm`。OK／キャンセル）を、ボタンの `data-confirm` で出す。キャンセルでは何も送らず、入力もそのまま残す。

確認を出す操作: 「先月と変更なし」での提出、取り下げ、下書きの削除、コメントの削除、確認完了とその取り消し、項目の無効化、すべての端末からのログアウト、予備のコードの作り直し、確認者の設定の保存、案件の終了、管理者の権限を付ける（`data-confirm-on`）、利用者の操作、臨時の調査の公開・締め切り・削除。

通常の提出では確認を出さない。客先名らしい言葉の注意が出ているときだけ、「客先名や個人名の注意が出ている欄が N か所あります。このまま送りますか？」と確かめる。

**画面を離れるときの確認**: 入力の多い画面（G-04 報告の作成・編集、G-07 臨時の調査の回答、G-12 項目の作成・編集）のフォームに `data-leave-warn="1"` を付ける。保存していない入力があるまま、リンク・戻る・タブを閉じるなどで画面を離れようとすると、ブラウザーの標準の確認（`beforeunload`。文言はブラウザーが決める）を出す。

| 状況 | 確認を出すか |
|---|---|
| 開いたまま何も入力していない | 出さない |
| 入力・選択を変えた | 出す |
| 開いた時点で保存していない内容がある（`data-unsaved="1"`。G-04 で過去の報告から写した直後、入力エラーや同じ月の報告の作成で戻った画面） | 出す |
| 自分でフォームを送った（保存・提出・写すなど。`data-confirm` でキャンセルしたときは除く） | 出さない |
| 自動保存が成功し、送ったあとに入力していない | 出さない |

### 11.5 画面の共通の配置（スマートフォン）

```text
┌──────────────────────────┐
│ 月次報告      [≡ メニュー] │ ← ヘッダー（「月次報告」はホームへのリンク）
├──────────────────────────┤
│ （メッセージ）              │
│                          │
│ 本文（1 列）               │
│                          │
├──────────────────────────┤
│ [ 主な操作のボタン ]        │ ← 画面の下に付いてくる（position: sticky）
└──────────────────────────┘
```

- 幅 360px で横にスクロールしない。ボタンの高さは 44px 以上（小さいボタンは 32px）。
- 項目名の横の小さな札: 社外秘は「社外秘」、限定は「限定」、必須は「必須」。
- メニューは `<details>` で開く。ログインが済んだ段階（`full`）だけ出す。ログアウトはメニューの中のボタン。メニューの高さは表示領域に収め（`max-height: calc(100dvh - 64px)`）、項目が多い役割（管理者・補佐・課長）ではメニューの中でスクロールして一番下のログアウトまで届くようにする。
- CSS・JavaScript は `asset_url()` で読み込み、URL にファイルの更新日時を付ける（`app.css?v=<更新日時>`）。本番を更新すると URL が変わるので、利用者のブラウザーが前のファイルを使い続けない（APP-093）。
- 色は CSS の変数で持ち、利用者が選んだ画面のテーマ（G-16 §4.5）で上書きする。新しく色を書くときは、直接の色ではなく変数を使う。
- 文字は **BIZ UDゴシック**で統一する（CSS の変数 `--font-body`。Windows 10 以降は標準で入っている）。`system-ui` は使わない（Windows では細い游ゴシックになり読みにくい）。BIZ UDゴシックがない端末（Linux・Mac）は Noto Sans JP・ヒラギノ角ゴ・メイリオの順で出す。入力欄・ボタンも本文と同じ字体にする（`font-family: inherit`）。Excel の出力（xlsx）の字体も BIZ UDゴシック。暗号の鍵・回復コードの表示だけは等幅の字体。
- 管理画面には、共通の道しるべ（パンくずと管理画面の切り替え）を出す（G-21 §4）。長い画面は節に分けてページの中のタブにする（G-21 §5）。
- メニューに出すのは、その人の役割で使える画面だけ。見出し「報告」「確認」「管理」「アカウント」でまとめる（`menu_items()` が見出しも返す）。

| メニュー | 出す人 |
|---|---|
| ホーム、自分の報告、アカウント設定 | 全員 |
| 提出状況 | 確認者、管理者 |
| 臨時の調査、出力 | 課長、管理者 |
| 項目マスタ | 管理者、課長、課別項目の管理者 |
| 案件の管理、組織・ユーザー、記録 | 管理者 |

削除データ（`admin/trash.php`）はメニューに出さず、記録の画面のリンクから開く。

## 12. 設定値（config.php）

| 名前 | 既定値 | 内容 |

## 画面確認の指摘による共通の見た目（APP-015・016・017・026・042・043・044）

- **日付**: 画面に出す日時は「2026/11/13 14:44」、日付だけは「2026/11/13」（`display_datetime()`・`display_date()`。K-045）。年月だけは「2026年11月」。記録の画面・CSV の値はハイフンの形のまま。
- **色**: 色は直接書かず、CSS の変数（`--tag-*`）で、既定とダーク（端末の設定の自動・選んだダーク）の両方の値を持つ。ダークで背景と文字の差が小さかった札・表の縞・説明文の色を直した。
- **項目の札**: 項目名の前に置く（報告の作成・報告の詳細・横並び）。必須＝赤の枠と文字、社外秘＝紫、限定＝赤の塗りと白い文字、注意＝黄に「!」。色だけでなく文字でも分かるようにする。
- **状態の札**: 報告の状態は `report_status_tag_html()` で、未作成＝灰の点線、下書き＝青、提出済み＝緑、確認完了＝緑の塗りと「✓」。回答待ち・未チェックは黄、回答あり・更新ありは青。
- **ボタン**: ボタンとリンクのボタンの高さを揃える。報告の詳細のチェックのボタンは横いっぱい。管理者のホームの入口はボタンの形。一覧（`.list`）のすぐ下に置くボタン（ホームの「コメントの一覧」、自分の報告の「もっと見る」）は、一覧の下の線から 12px 離す（`.list + .button`。APP-102）。
- **表**: 操作の列（`td.actions`）は表のセルのまま（行の段がずれない）。
- **テーマの飾り**: さくらは、淡い桜色から白へのグラデーションの背景、ヘッダーの下の桜色の線、右上と左に垂れ下がる桜の枝（五弁の花・しべ・つぼみ。CSS の中の SVG）、先に切れ込みのある花びらが裏返りながら舞う（`.theme-decoration`。画面に固定した押せない飾りの層なので、スマートフォンでスクロールしても途切れない。端末で「動きを減らす」を選んでいるときは花びらを出さず（枝は動かないので出す）、印刷では飾りを出さない）。夜桜は、さくらから派生した暗いテーマで、夜空の紺のグラデーションの背景（ヘッダーも紺。カードなどの面は紫寄りの黒）に満月（淡い光の輪）と小さな星、ヘッダーの下の桜色の線、さくらと同じ枝と花びら（少し透かす）。スマートフォンの幅では本文で空が隠れるので、月はヘッダーの中に小さく出す。夜桜2 は夜桜1 と同じ作りで、桜だけをソメイヨシノの色（彩度を下げて明るくし、ほんのり光らせる。CSS の `filter`）にする。共通の規則は `[data-theme^="yozakura"]` で書く。若葉は、上から淡い若草色が薄れていく背景に、左上から差す木漏れ日（柔らかい光・斜めの淡い光の筋・小さな光の粒）、ヘッダーの下の若草色の線、右上と左に垂れ下がる若葉の枝（葉の濃淡・葉脈・新芽。CSS の中の SVG。左は右の絵を左右に返す）、小さな若葉がゆっくり舞い落ちる（さくらの花びらと同じ動き。数を減らしてゆっくり。「動きを減らす」のときは出さない）。見出しの印は 🌱。若葉2 は若葉と同じ作りで、左下の隅に、奥から手前へ蛇行するせせらぎ（水・苔の岸・石・草。飾りの層の 6 番目の span。CSS の中の SVG）を足す。白いさざ波は流れに沿って奥から手前へ動き、水面がきらめく（SVG の中の動き。「動きを減らす」のときは動きのない絵に替える）。PC では本文の外の余白に収まる。共通の規則は `[data-theme^="wakaba"]` で書く。
- **見分けやすい色**（`cud`。カラーユニバーサルデザイン）: 色覚の型に関係なく見分けやすいテーマ。画面では「見分けやすい色（カラーユニバーサルデザイン）」と出し、誰が選んでもよい。
  - 配色: 赤と緑の対比をやめ、青（済み・強調。ボタン・リンク）、黄（注意・待ち）、朱（エラー・限定）で分ける（カラーユニバーサルデザイン推奨配色セットを土台）。社外秘は灰色の点線の枠。文字と背景の明るさの比は 7 以上。飾りはない。
  - 形の印（このテーマのときだけ）: 札の頭に印を付ける（未作成 －、下書き ✎（点線の枠）、提出済み ●、確認完了 ✓、待ち …、変わった・対応中 ◆、解決・完了 ✓、必須 ＊、限定 ■、社外秘 ◇、注意 !）。札の枠を太く、知らせ（エラー ×・成功 ✓）の左の線を太く。提出状況の棒は斜線の模様（確認完了は逆向きの細い斜線）、地は白で枠を濃く。キーボードで選んだところの枠を太い黄にする。
  - 確かめ方: 画面確認の道具（`screen_gallery.py`）の `--vision` で、ブラウザーの色覚の型の見え方の真似（P 型・D 型・T 型・色の区別なし）で撮れる。
- **選んだテーマ**: アカウント設定のテーマの選択は、選んだものを枠と背景で目立たせる。
