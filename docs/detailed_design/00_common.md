## 2. URL の決まり

| 決まり | 内容 |
|---|---|
| 画面 | GET で開く。画面を開くだけでデータは変えない |
| 更新 | POST だけで受ける。処理のあとは結果の画面へ転送する（PRG） |
| ID の受け取り | `input_id()` で受け、1 以上の整数（10 桁まで）の文字列でなければ 400 |
| 対象月 | `YYYY-MM`。正規表現 `^\d{4}-(0[1-9]|1[0-2])$` で確かめる |
| 転送先 | 自分のサイトの中のパスだけ（`/` で始まり、`//` で始まらず、`\` と制御文字を含まない）。それ以外は `/index.php` にする。転送は 303 |
| 未ログイン | どの階層の画面からでも、`/report-system/login.php?next=<元の画面>` へ転送する（`next` は `base_path` を除いた自サイトのパスだけ受け付ける。POST のときと、`/login.php` で始まるものは付けない） |

## 3. すべての要求で行う共通処理

基本設計書 §15.1。`bootstrap.php` は設定の読み込み、時刻帯・文字コードの設定、共通の処理の読み込み、エラーの扱いの設定（画面に詳細を出さない）だけを行う。失敗したときは 500「ただいま利用できません」。

各画面の処理は、最初に `page_start()`（`session.php`）を呼ぶ。`page_start()` は次を順に行う。

| 順 | 処理 | 失敗したとき |
|---|---|---|
| 1 | 共通のヘッダーを付ける（§4） | — |
| 2 | セッションの開始 | — |
| 3 | DB に接続し、`PRAGMA foreign_keys = ON`、`PRAGMA busy_timeout = 5000`、`PRAGMA journal_mode = WAL` | 503 |
| 4 | ログイン不要の画面（ログイン・再設定）は、POST なら CSRF の確認をしてここで終わる | 403 |
| 5 | ログインの確認。自動ログアウト（操作がない時間・最長の時間）、`is_active`、`session_version` の確認（§5） | ログイン画面へ |
| 6 | 2 段階認証が未設定の段階（`setup`）なら、G-16 の設定だけ使える | G-16 の 2 段階認証へ |
| 7 | パスワードの変更が必要な人（`must_change_password = 1`）は、G-16 のパスワード変更だけ使える | G-16 のパスワードへ |
| 8 | POST なら CSRF の確認（§6） | 403 |

`page_start()` のあとに、画面ごとの処理で次を行う。

| 順 | 処理 | 失敗したとき |
|---|---|---|
| 9 | 画面ごとの権限の確認（§10） | 403 |
| 10 | POST なら送信の番号の確認（§7） | 1 回目の結果を返す／処理中の案内 |
| 11 | 画面ごとの処理（入力の確認 → 状態の確認 → 1 つのトランザクションで更新 → 記録） | 入力エラーは同じ画面に戻す |

- パスワードだけ済んで 2 段階認証のコードを待っている間は、セッションに `pw_uid` と `pw_at` だけを持つ（`pw_stage_minutes` 分だけ有効）。ログインの状態ではないため、ほかの画面を開くとログイン画面へ戻る。
- 稼働の確認（`health.php`）は `page_start()` を通らない（§14）。

## 4. 共通のヘッダー

| ヘッダー | 値 | 目的 |
|---|---|---|
| `Cache-Control` | `no-store` | 画面の内容を端末に残さない |
| `Pragma` | `no-cache` | 同上（古いブラウザー向け） |
| `X-Frame-Options` | `DENY` | 他のサイトへの埋め込みを防ぐ |
| `X-Content-Type-Options` | `nosniff` | |
| `Referrer-Policy` | `same-origin` | |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; form-action 'self'; frame-ancestors 'none'; base-uri 'none'` | 外部の読み込みと埋め込みのスクリプトを禁止する |

`Strict-Transport-Security` はまだ付けていない。本番で HTTPS の動作を確認してから付ける。

公開ディレクトリの `.htaccess` では次を行う。

- HTTP で来た要求を HTTPS へ転送する（301）。さくらのレンタルサーバーは SSL をプロキシで終えるため、`HTTPS` が off で、かつ `X-Sakura-Forwarded-For` が空のときだけ転送する。
- ファイルの一覧を出さない（`Options -Indexes`）。
- `_boot.php` を直接開かせない。
- `.sqlite .sqlite3 .db .key .bak .backup .log .md .sql .json .ini .sh .py` を拒否する。

## 5. セッションと自動ログアウト

| 項目 | 値 |
|---|---|
| Cookie | 名前は `mr_session`（端末の記憶は `mr_device`）。`HttpOnly`、`SameSite=Lax`。`Secure` は設定 `https` に従う。パスは `base_path` ＋ `/`（`base_path` が空なら `/`）。`session.use_strict_mode` と `use_only_cookies` を有効にする |
| ID の作り直し | パスワードが合ったとき、ログインの完了時（2 段階認証が未設定の `setup` の段階を含む）、2 段階認証の設定の完了時、パスワード変更時に `session_regenerate_id(true)` |
| 操作がないときのログアウト | 30 分。「一定時間操作がなかったため、ログアウトしました。」と出す |
| ログインの最長 | 12 時間。同上 |
| 利用者の状態 | `is_active = 0` になった人はログアウトさせる |
| すべての端末からログアウト | `users.session_version` を 1 増やし、記憶した端末もすべて消す。セッションに持つ版と違えばログアウトさせる。2 段階認証の設定とパスワードの変更・再設定でも版を上げる |
| ログアウト | POST だけで受ける。セッションを破棄し、Cookie を消す。端末の記憶は残す（G-16 で消せる） |

## 6. CSRF

- セッションごとに 32 バイトの乱数のトークン（16 進 64 文字）を作り、すべてのフォームに隠し項目 `csrf_token` で入れる。
- POST を受けたら `hash_equals()` で比べる。違えば 403「画面を開き直してから、もう一度お試しください」。ログイン不要の画面（ログイン・再設定）でも確かめる。
- 自動保存などの JavaScript からの送信も、同じトークンをフォームの値として付ける（ヘッダー `X-CSRF-Token` でも受け付ける）。

## 7. 送信の番号（二重登録の防止）

基本設計書 §15.3。

| 項目 | 内容 |
|---|---|
| 番号の作成 | 画面を作るときに、更新のフォームごとに 16 バイトの乱数（16 進 32 文字）を隠し項目 `request_key` で入れる（`form_hidden()`）。形が違えば 400 |
| やり直し | 番号は隠し項目のため、同じ画面から送り直せば同じ番号になる。自動保存は送るたびに JavaScript が新しい番号を作る |
| サーバーの処理 | `request_keys` に番号を登録してから処理する。登録済みで `done` なら、処理せずに「前の送信で処理済みです。」と出して 1 回目の結果（転送先）へ移す。`processing` なら 409「前の送信をまだ処理しています。しばらく待ってから画面を読み直してください。」 |
| 別の人・別の操作 | 同じ番号でも利用者か操作が違えば 400 |
| 入力エラー | 控えを消し（`rk_cancel()`）、直して送り直せば処理する。409 以外のエラーの画面を出すときも、処理中の控えを消す |
| 控えの期間 | 1 日。それより古いものは、1 日 1 回の後片付け（ログイン画面を開いたとき）で消す |

## 8. 暗号化

基本設計書 §8.1、§11.1。

### 8.1 対象

| 対象 | 暗号化する |
|---|---|
| 自由記述の値（`single_text`、`multi_text`、`table`。`table` は列の種類を問わず全体） | 常に |
| 機密区分が「限定」の項目の値（種類を問わない） | 常に |
| コメントの本文 | 常に |
| 変更履歴の変更前・変更後（対象の項目が暗号化の対象なら） | 常に |
| 臨時の調査の回答（上と同じ決まり） | 常に |
| 2 段階認証の秘密の値 | 常に |
| 選択式の値、数値、日付、年月、案件コード（通常・社外秘） | しない |

### 8.2 方式

| 項目 | 内容 |
|---|---|
| 方式 | AES-256-GCM（PHP の OpenSSL 機能。PHP 7.4 で使える） |
| 鍵 | 32 バイトの乱数。`keys/field_<版>.key`（今は `field_v1.key`）に Base64 で保存（権限 600）。DB・公開ディレクトリとは別の場所。`app/bin/migrate.php` が、なければ作る |
| 保存の形 | `v1:` ＋ Base64（IV 12 バイト ＋ 認証タグ 16 バイト ＋ 暗号文）。`v1` は鍵の版 |
| 付加データ | テーブル名と行の識別（例: `rfv:<report_id>:<field_id>:<block>`）を付加データにする。暗号文を別の行に移し替えても復号できない。一覧は DB 編 §4 |
| 鍵の入れ替え | 復号のときは先頭の版で鍵のファイルを選ぶ。新しい鍵を `v2` として追加し、全件を暗号化し直す処理はまだ作っていない |
| 復号の失敗 | 画面には「この内容は表示できません」と出し、ログに記録する |

### 8.3 検索

自由記述は DB では検索できないため、検索の条件（対象月・課・選択式の値）で絞った報告を、見る権限のある範囲だけ復号して、アプリの中で文字列を探す。1 回の検索で復号する報告の上限は `search_decrypt_limit`（既定 2,000 件）で、超えるときは条件を足すよう案内する。探す項目は項目マスタの `is_searchable` で決める。画面と処理は G20_search.md。

## 9. 入力の確認

### 9.1 3 段階（基本設計書 §15.2）

| 段階 | 場所 | 内容 |
|---|---|---|
| 1 | 画面 | HTML の `required`、`maxlength`、`type`、`min`/`max`。補助であり、頼らない |
| 2 | サーバー | 項目マスタの設定に従い、すべてを確認し直す（§9.2） |
| 3 | サーバー（DB を見る） | 重複、存在、状態（例: 確認完了の報告は変更できない） |

### 9.2 入力部品ごとの確認

| 種類 | 確認 | 保存の形 |
|---|---|---|
| `single_text` | 改行なし。制御文字なし。UTF-8 として正しい。最大文字数（設定。既定 200 文字） | 文字列（暗号化） |
| `multi_text` | 制御文字は改行・タブのみ可。改行は LF にそろえる。最大文字数（設定。既定 2,000 文字） | 文字列（暗号化） |
| `date` | `YYYY-MM-DD` で、実在する日付 | 文字列 |
| `month` | `YYYY-MM` | 文字列 |
| `number` | 整数部 12 桁まで、負の数も可。最小・最大・小数の桁数（設定） | 数字の文字列 |
| `select`・`radio` | 選択肢のコードのどれか（有効なもの。無効にした選択肢も、保存済みの値から変えていなければ受け付ける） | 選択肢のコード |
| `checkbox` | `0`・`1`・空 | `1`／空 |
| `multi_check` | 選択肢のコードの集合。重複なし（無効の選択肢の扱いは `select` と同じ） | JSON の配列 |
| `table` | 行数の上限（設定 `max_rows`。既定 20 行）。すべて空の行は捨てる。各セルは制御文字なし（改行は `multi_text` の列だけ可）、2,000 文字以内だけを確かめる（数値・日付・選択肢の確認はしない）。列の種類は `single_text`・`multi_text`・`number`・`date`・`select` | JSON の配列（全体を暗号化） |

- 文字数は `mb_strlen()` で数える（`mbstring` がない環境では `preg_match_all('/./us')` で数える）。
- 前後の空白は取り除いてから確認する。
- 空の値は空の文字列で保存する（`multi_check` で何も選ばないときも空）。
- 必須の確認は「提出」のときだけ行う。下書きの保存では行わない。

### 9.3 客先名らしい言葉の注意

- 自由記述の値に、`warning_words` の言葉が含まれるかを、画面（入力中）とサーバー（保存時）の両方で調べる。
- 含まれても保存は止めない。サーバーは、含まれた自由記述の欄を `report_field_values.has_warning = 1` にする（確認者の画面の印に使う）。
- 調べるときは、全角・半角と大文字・小文字をそろえてから比べる（サーバーは `mb_convert_kana('asKV')` のあと小文字に、画面は全角英数字・全角空白を半角にしてから小文字にする）。
- 欄の下に「客先名や個人名が含まれていませんか」と出す。
- 初期の言葉は 14 個（`株式会社`、`(株)`、`㈱`、`有限会社`、`様`、`御中`、`Inc.`、`Ltd.` など）。`schema_ensure()` が登録する。

## 10. 権限の判定

`perm.php` にまとめ、画面ごとの処理は必ずここを通す。

### 10.1 役割の判定

| 役割 | 判定 |
|---|---|
| 管理者 | `users.is_admin = 1`（`is_admin()`） |
| システム管理者補佐 | `users.is_admin_deputy = 1`（`is_admin_deputy()`）。管理の画面は `can_manage_system()`（管理者か補佐）・`require_system_manager()` で開ける。個々の情報を出す所は、画面ごとに `is_admin()` で分ける（G-14 §6.9） |
| 課長（その課の最終確認者） | `department_reviewers` に `(課, 本人, is_final = 1)` がある |
| 確認者（その課） | `department_reviewers` に `(課, 本人)` がある（課長を含む） |
| 課別項目の管理者 | `department_admins` に `(課, 本人)` がある、その課の課長、または管理者・補佐 |
| 部下 | 上のどれでもない、ログインしている利用者 |

役割は課ごとに決まる。同じ人が、ある課の確認者で、別の課では部下ということもありうる。

### 10.2 報告を見られるか

```text
削除済みの報告                     → だれも見られない（404）
本人の報告                         → 見られる
下書き                             → 本人だけ
報告の課（作成時の課）の確認者      → 見られる（ただし「限定」の項目は課長だけ）
報告の課を引き継いだ課の確認者      → 見られる（同上。組織の改訂。G-14 §6.6）
本人の今の課の確認者                → 見られる（同上。報告は人について回る。課を移った人の移る前の報告）
「班ごと」の課で担当の班がある確認者 → 本人の今の班がその班のときだけ（課長は班に関係なく見る。G-14 §6.7）
それ以外（管理者を含む）            → 見られない（存在しない報告と同じ 404 を返す）
```

判定は `reviewer_can_see_report()`（`perm.php`）。確認者の設定 1 行ごとに「その課と、引き継いだ前の課」「課長か」「担当の班」を持ち（`report_view_grants()`）、報告の課か本人の今の課（`user_current_placement()`）に当たるかを見る。

「チェック n/m」の m（チェックを求める確認者）は、報告を作ったときの課（と引き継いだ課）の有効な確認者のうち、その報告を見られる人（`report_expected_reviewer_ids()`。班ごとの課では担当の班の確認者と、課全体の確認者・課長）。チェックの操作もこの人たちだけができる。課を移った人の移る前の報告を新しい課の確認者が見られても、チェックは求めない。

管理の権限と、報告を見る権限は分ける（基本設計書 §8）。管理者でも、確認者でない課の報告の中身は見られない（`can_view_report()`・`can_view_restricted()` は管理者を特別に扱わない）。中身を出す画面の課の一覧は `reviewable_departments()`（確認者の課だけ）、課長の画面は `final_departments()`（課長の課だけ）。提出状況（G-08）だけは `status_departments()` で、管理者は全課を見られる（中身は出さず、報告へのリンクも出さない）。

### 10.3 機密区分による表示

| 区分 | 本人 | 確認者 | 課長 | 管理者（確認者でない課） |
|---|---|---|---|---|
| 通常・社外秘 | ○ | ○ | ○ | × |
| 限定 | ○ | 「（限定のため表示しません）」 | ○ | × |

## 11. メッセージと画面の共通部品

### 11.1 メッセージの出し方

| 種類 | 出し方 |
|---|---|
| 成功 | 本文の上に出す（自動では消えない） |
| 入力エラー | 本文の上にまとめて出し、該当する欄の下にも出す。消えない |
| 注意（客先名らしい言葉など） | 該当する欄の下に黄色で出す |
| エラー（権限・障害） | 専用の画面。英語や内部の情報は出さない |

文言は `msg('既定の文言', [差し込み])` で出し、課長が G-17 で変えられる（G-01・G-02 の文言は固定）。JavaScript の文言は `M()`。仕組みは G17_messages.md §4。

### 11.2 共通のエラー画面

| 状態 | 文言 |
|---|---|
| 400 | 要求の内容が正しくありません。画面を開き直してください |
| 403 | この操作を行う権限がありません |
| 403（CSRF） | 画面を開き直してから、もう一度お試しください |
| 404 | 対象のデータが見つかりません |
| 409 | 前の送信をまだ処理しています。しばらく待ってから画面を読み直してください |
| 500・503 | ただいま利用できません。時間をおいてもう一度お試しください |

- 文言の終わりには「。」を付ける。画面ごとに別の文言を出すこともある（例: 「出力は PC から行ってください。」）。
- エラーの画面にはメニューを出さず、「ホームへ戻る」のリンクだけを出す。

### 11.3 通信が切れたとき（JavaScript）

| 状況 | 動き |
|---|---|
| 保存・提出 | 通常のフォームの送信。押したあと 30 秒は、同じフォームを二重に送らせない |
| 送り直し | 送信の番号は隠し項目のため、同じ画面から送り直せば同じ番号になる（二重には登録されない） |
| 自動保存 | 入力が変わったときだけ 60 秒ごとに送る。30 秒応答がないか通信のエラーなら「通信が切れたため自動保存できませんでした。入力は残っています」と出す |

### 11.4 確認の表示

ブラウザーの標準の確認（`window.confirm`。OK／キャンセル）を、ボタンの `data-confirm` で出す。キャンセルでは何も送らず、入力もそのまま残す。

確認を出す操作: 「先月と変更なし」での提出、取り下げ、下書きの削除、コメントの削除、確認完了とその取り消し、項目の無効化、すべての端末からのログアウト、予備のコードの作り直し、確認者の設定の保存、案件の終了、管理者の権限を付ける（`data-confirm-on`）、利用者の操作、臨時の調査の公開・締め切り・削除。

通常の提出では確認を出さない。客先名らしい言葉の注意が出ているときだけ、「客先名や個人名の注意が出ている欄が N か所あります。このまま送りますか？」と確かめる。

**画面を離れるときの確認**: 入力の多い画面（G-04 報告の作成・編集、G-07 臨時の調査の回答、G-12 項目の作成・編集）のフォームに `data-leave-warn="1"` を付ける。保存していない入力があるまま、リンク・戻る・タブを閉じるなどで画面を離れようとすると、ブラウザーの標準の確認（`beforeunload`。文言はブラウザーが決める）を出す。

| 状況 | 確認を出すか |
|---|---|
| 開いたまま何も入力していない | 出さない |
| 入力・選択を変えた | 出す |
| 開いた時点で保存していない内容がある（`data-unsaved="1"`。G-04 で過去の報告から写した直後、入力エラーや同じ月の報告の作成で戻った画面） | 出す |
| 自分でフォームを送った（保存・提出・写すなど。`data-confirm` でキャンセルしたときは除く） | 出さない |
| 自動保存が成功し、送ったあとに入力していない | 出さない |

### 11.5 画面の共通の配置（スマートフォン）

```text
┌──────────────────────────┐
│ 月次報告      [≡ メニュー] │ ← ヘッダー（「月次報告」はホームへのリンク）
├──────────────────────────┤
│ （メッセージ）              │
│                          │
│ 本文（1 列）               │
│                          │
├──────────────────────────┤
│ [ 主な操作のボタン ]        │ ← 画面の下に付いてくる（position: sticky）
└──────────────────────────┘
```

- 幅 360px で横にスクロールしない。ボタンの高さは 44px 以上（小さいボタンは 32px）。
- 項目名の横の小さな札: 社外秘は「社外秘」、限定は「限定」、必須は「必須」。
- メニューは `<details>` で開く。ログインが済んだ段階（`full`）だけ出す。ログアウトはメニューの中のボタン。
- 色は CSS の変数で持ち、利用者が選んだ画面のテーマ（G-16 §4.5）で上書きする。新しく色を書くときは、直接の色ではなく変数を使う。
- 管理画面には、共通の道しるべ（パンくずと管理画面の切り替え）を出す（G-21 §4）。長い画面は節に分けてページの中のタブにする（G-21 §5）。
- メニューに出すのは、その人の役割で使える画面だけ。見出し「報告」「確認」「管理」「アカウント」でまとめる（`menu_items()` が見出しも返す）。

| メニュー | 出す人 |
|---|---|
| ホーム、自分の報告、アカウント設定 | 全員 |
| 提出状況 | 確認者、管理者 |
| 臨時の調査、出力 | 課長、管理者 |
| 項目マスタ | 管理者、課長、課別項目の管理者 |
| 案件の管理、組織・ユーザー、記録 | 管理者 |

削除データ（`admin/trash.php`）はメニューに出さず、記録の画面のリンクから開く。

## 14. 稼働の確認（health.php）

- ログイン不要。`page_start()` を通らず、自分で DB に接続する。
- DB に `SELECT 1` を流し、成功なら `200 OK` と本文 `ok`、失敗なら `503` と本文 `ng` だけを返す（`Content-Type: text/plain`、`Cache-Control: no-store`）。

## 画面確認の指摘による共通の見た目（APP-015・016・017・026・042・043・044）

- **日付**: 画面に出す日時は「2026/11/13 14:44」、日付だけは「2026/11/13」（`display_datetime()`・`display_date()`。K-045）。年月だけは「2026年11月」。記録の画面・CSV の値はハイフンの形のまま。
- **色**: 色は直接書かず、CSS の変数（`--tag-*`）で、既定とダーク（端末の設定の自動・選んだダーク）の両方の値を持つ。ダークで背景と文字の差が小さかった札・表の縞・説明文の色を直した。
- **項目の札**: 項目名の前に置く（報告の作成・報告の詳細・横並び）。必須＝赤の枠と文字、社外秘＝紫、限定＝赤の塗りと白い文字、注意＝黄に「!」。色だけでなく文字でも分かるようにする。
- **状態の札**: 報告の状態は `report_status_tag_html()` で、未作成＝灰の点線、下書き＝青、提出済み＝緑、確認完了＝緑の塗りと「✓」。回答待ち・未チェックは黄、回答あり・更新ありは青。
- **ボタン**: ボタンとリンクのボタンの高さを揃える。報告の詳細のチェックのボタンは横いっぱい。管理者のホームの入口はボタンの形。
- **表**: 操作の列（`td.actions`）は表のセルのまま（行の段がずれない）。
- **テーマの飾り**: さくらは、淡い桜色から白へのグラデーションの背景、ヘッダーの下の桜色の線、右上と左に垂れ下がる桜の枝（五弁の花・しべ・つぼみ。CSS の中の SVG）、先に切れ込みのある花びらが裏返りながら舞う（`.theme-decoration`。画面に固定した押せない飾りの層なので、スマートフォンでスクロールしても途切れない。端末で「動きを減らす」を選んでいるときは花びらを出さず、印刷では飾りを出さない）。若葉は、上から淡い若草色が薄れていく背景、ヘッダーの下の若草色の線、左右の上に若葉の枝、画面の下の隅に淡い若葉がゆっくり揺れる飾り（模様は使わない。見出しの印は 🌱。枝と葉は固定の飾りの層）。
- **選んだテーマ**: アカウント設定のテーマの選択は、選んだものを枠と背景で目立たせる。

- ログインして使う全画面（ログイン・パスワードの再設定・エラー・印刷用の画面を除く。K-047 決定）の上に「？ この画面の使い方」を出す（押すと開く。`screen_help_text()`）。最後に「よくある質問」（G-25）へのリンク。
- 文は `msg()` で書いてあるので、メッセージ（G-17）の画面で変えられる。
