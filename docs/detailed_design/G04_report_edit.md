# G-04 報告の作成・編集

| 項目 | 内容 |
|---|---|
| URL | `/reports/edit.php?period=YYYY-MM`（GET: 画面）、`/reports/save.php`（POST: 下書き保存・提出・変更なしで提出・提出後の保存・取り下げ・削除・自動保存） |
| 利用者 | 本人（報告を作る人） |
| 主な端末 | スマートフォン |
| 段階 | 1（前月の引き継ぎ・変更なし・提出後の追記は 2） |
| 関連する機能 | F-05、F-10、F-11、F-20、F-23 |

---

## 1. 目的

様式（共通項目＋所属課の課別項目）に従って入力画面を組み立て、月次報告を作る・直す・提出する。**前月の内容が入った状態で開き、変わったところだけ直せばよい**ようにする。

## 2. 表示の条件と権限

| 状態 | 本人 | ほかの人 |
|---|---|---|
| 未作成 | 作成できる | 開けない |
| 下書き | 編集・提出・削除できる | 開けない（G-05 は管理者だけが見られる） |
| 提出済み | 追記・修正できる（変更履歴が残る）。取り下げできる | 開けない（G-05 で見る） |
| 確認完了 | 開くと G-05 へ転送する | 開けない |

- 本人だけが作成・編集できる。`edit.php`・`save.php` は、ログインしている人の `(user_id, period)` の報告だけを扱う（管理者の代理編集はない）。
- 所属課が設定されていない人は、報告がまだないときだけ、400「所属の課が設定されていません。管理者に連絡してください。」で止める。
- 対象月は、当月と過去 3 か月まで（未来の月は不可）。GET は 400「作成できるのは、当月と過去 3 か月までの報告です。」、POST は文言なしの 400。

## 4. 表示項目

### 4.1 様式の組み立て

1. 対象の課 = 本人の所属課（報告が既にあれば、報告の `department_id`）。
2. 新しく作るときは、`report_fields` から `is_active = 1` かつ（`department_id IS NULL` または対象の課）の項目を、共通項目→課別項目、`sort_order`、`id` の順に並べる。最初の保存で報告を作るときに、`report_record_fields` に定義を写す（以後、この報告はこの定義で表示する）。
3. 既にある報告は、`report_record_fields` の定義で組み立てる（項目マスタをあとで変えても、この報告の見え方は変わらない）。
4. `field_scope = 'project'` の項目は案件ブロックの中に、`'report'` の項目は「報告全体」の欄に出す。
5. `settings_json.show_when`（例: 進捗が「遅延あり」のときだけ「進捗の補足」を出す）は、画面の JavaScript で表示を切り替える。サーバーは、条件を満たさない欄の値を空として扱い、必須の誤りも消す。

### 4.2 入力部品の出し方

| 種類 | 部品 |
|---|---|
| `project` | プルダウン（有効な `projects` のうち、所属課の案件と課の指定がない案件。表示は「コード 社内向けの呼び名」）。案件ブロックごとに 1 つ |
| `single_text` | `<input type="text">`（`maxlength` は設定。既定 200） |
| `multi_text` | `<textarea>`（`maxlength` は設定。既定 2,000。高さは利用者が変えられる） |
| `date`・`month` | `<input type="date">`・`<input type="month">` |
| `number` | `<input type="number" inputmode="decimal">`（`step` は小数の桁、`min`・`max` は設定） |
| `select` | `<select>`（先頭は「選んでください」） |
| `radio` | ラジオボタン。必須でない項目には「未選択」を足す |
| `checkbox` | チェック 1 つ（表示は「はい」） |
| `multi_check` | チェックボックス |
| `table` | 列ごとの入力欄の表。保存済みの行に空の行を 2 つ足して出す。注記「行が足りないときは、保存すると空の行が増えます。」。すべて空の行は保存しない |

- 項目名の横に、必須の札と、機密区分の札（社外秘・限定）を出す。
- 説明文（`help_text`）を欄の下に、入力例（`placeholder`）を欄の中に出す。
- 自由記述の欄には「客先名・固有名詞・個人名は書かないでください。」を常に出す。
- 無効にした選択肢は、保存済みの値と同じものだけ出す。

### 4.3 前月からの引き継ぎ（段階 2）

まだ報告がない月を開いたとき、同じ人の、対象月より前でいちばん新しい報告（状態は問わず下書きも含む。削除済み・移行データは除く）を引き継ぎ元にして、次を写す。

| 対象 | 写すもの |
|---|---|
| 案件ブロック | 引き継ぎ元の案件ブロックをすべて。ただし、無効になった案件は写さず、「前月の案件 P-0007 は終了したため外しました」と出す |
| 項目の値 | `carry_over = 1` の項目（`project` 型を除く）の値。種類が同じもの、`single_text`→`multi_text`、`select`↔`radio` だけ写す。選択式は今の定義で有効な選択肢だけ（`multi_check` は有効な選択肢だけを残す） |
| 自由記述 | `carry_over = 1` なら写す（復号して画面に入れ、保存のときに新しい報告用に暗号化する） |

引き継いだときは「前月の内容を入れてあります。変わったところだけ直してください。」を出す。`copied_from_id` は、最初の保存で報告を作るときに引き継ぎ元を探し直して入れる。

## 5. 入力項目と確認

- 項目ごとの確認は共通編 §9.2 に従う。設定は `report_record_fields.settings_json` を使う。
- 案件ブロック:
  - 同じ案件を 2 つ入れられない（「同じ案件が 2 つあります」）。
  - 選べない案件は「この案件は選べません」（報告にすでにある案件は、終了していても可）。
  - 既存のブロックの案件を空にすると「案件を選んでください（外すときは「この案件を外す」）」。
  - 11 件以上は「案件は 10 件までにしてください」。
  - 案件を選んでいない「案件を追加するとき」の欄と、「この案件を外す」にチェックしたブロックは保存しない。
- 必須の確認は、**提出のとき**と**提出済みの報告を保存するとき**だけ行う。下書きの保存と自動保存では行わない。
- 「先月から変更なしで提出」は、送られた入力を使わず、引き継ぎの値（§4.3）で提出する。
  - 必須が足りなければ保存せず、引き継いだ値を入れた画面に戻し、「前月の内容に入力が必要な項目があります。入力して「提出する」を押してください。」を出す。
  - 引き継ぎ元がないのに送ると、400「前月の報告がないため、「変更なし」では提出できません。」。
  - 下書きがあるときは、下書きの内容が前月の内容に置き換わる（確認の表示で知らせる）。

## 6. 操作と処理

すべて `/reports/save.php` に POST する。`action` は `draft`／`submit`／`unchanged`／`save`／`withdraw`／`delete`／`autosave` の 7 つ（それ以外は 400）。共通: CSRF の確認（共通編 §3）→ 対象月の確認 → 送信の番号の確認（控えは `report.<action>`）→ 状態の確認 → 入力の確認 → 1 つのトランザクション → 転送。入力の誤りでは送信の番号の控えを消し、入力した値と誤りの欄を示して同じ画面に戻す（何も保存しない）。

### 6.1 画面を開く（GET）

1. `period` を確かめる。本人の `(user_id, period)` の報告を探す（`is_legacy = 0`、削除されていないもの）。
2. なければ、まだ作らずに、§4.1・§4.3 で組み立てた入力画面を出す（最初の保存で作る）。
3. 確認完了なら G-05 へ転送する。

### 6.2 下書き保存（`action=draft`）・自動保存（`action=autosave`）

1. 報告がなければ作る（`status = 'draft'`）。`report_record_fields` に定義を写す。一意の索引 `ux_report_user_period` で 1 件に守る。2 つの端末から同時に作ると、片方は一意の索引で失敗してエラー画面になる（同じ送信の番号の 2 回目は、送信の番号の仕組みで 1 回目の結果へ転送する）。
2. 案件ブロック: 残すものは同じ行を使い（コメントの紐付けを保つ）、並び順だけ更新する。外したブロックは値と一緒に消す。
3. 値を保存する。自由記述と「限定」は暗号化。客先名らしい言葉があれば `has_warning = 1`。
4. 下書き保存のあとは G-04 に戻り「下書きを保存しました」。
5. 自動保存は、画面の JavaScript が**入力が変わったときだけ、60 秒ごと**に送る（共通編 §11.3）。下書き（未作成を含む）のときだけ行う。応答は JSON。
   - 成功: `{"ok":true,"saved_at":"10:42"}`
   - 提出済み: `{"ok":false,"reason":"not_draft"}`
   - 入力の誤り: `{"ok":false,"reason":"invalid"}`（画面に「自動保存できませんでした（入力を確かめてください）」）

### 6.3 提出（`action=submit`・`action=unchanged`）

1. 必須を確かめる。足りなければ保存せずに、入力した値と足りない欄を示して戻す。
2. 客先名らしい言葉の注意が出ている欄があれば、画面の JavaScript が確認を出す（共通編 §11.4）。サーバーは止めない。
3. 下書きの保存と同じ処理のあと、`status = 'submitted'`、`submitted_at`。`report_status_history` に記録。
4. 「先月から変更なしで提出」のときは `unchanged = 1`。
5. G-05 へ転送し「提出しました」。

### 6.4 提出後の追記・修正（`action=save`、状態が提出済み）

1. 値を比べ、変わった値ごとに `report_value_history` に変更前・変更後を残す（暗号化の対象なら暗号化したまま）。
2. 値の変更か、案件ブロックの追加・削除が 1 つでもあれば `revision + 1`。チェック済みの確認者は「更新あり」になる（`report_reviews.checked_revision < revision`）。
3. 変わったものがなければ `revision` は上げない。
4. G-05 へ転送し「保存しました。変更があれば確認者に知らせます」。再提出の操作はない（基本設計書 §4.1）。

### 6.5 取り下げ（`action=withdraw`、状態が提出済み）

確認の表示「提出を取り下げて下書きに戻します。よろしいですか？」のあと、1 つのトランザクションで `status = 'draft'` にし、`report_status_history` に記録する。チェックはそのまま残す。G-04 に戻り「提出を取り下げました」。

### 6.6 下書きの削除（`action=delete`、状態が下書き）

確認の表示「この下書きを削除します。よろしいですか？」のあと、`deleted_at` を入れてホームへ戻り「下書きを削除しました」。30 日間は管理者が戻せる（G-15）。

## 9. 検証の観点

- ほかの人の報告の `period` を指定しても、自分の報告しか開けない（ほかの人の ID を POST しても断られる）。
- 同じ送信の番号で 2 回提出しても、提出は 1 回。2 つの端末から同時に新規作成しても、報告は 1 件。
- 下書きでは必須を確かめず、提出では確かめる。隠れた欄（`show_when`）は必須でも空でよい。
- 項目マスタを変えたあとも、既にある報告は作成時の定義で表示・保存される。
- 無効にした選択肢の値は、前月から引き継がれない。
- 前月の値が引き継がれる。「先月から変更なしで提出」で `unchanged = 1` になる。
- 提出後の修正で `revision` が上がり、チェック済みの確認者が「更新あり」になる。変更がなければ上がらない。
- DB に自由記述が平文で入っていない。
- 確認完了の報告に POST しても変わらない（400）。
- 案件ブロック 0 件・10 件、自由記述の上限ちょうど・1 文字超えで動きが正しい。

自動の検証でまだ試していないもの: ほかの人の `period`、同時の新規作成、案件ブロック 0 件・10 件、文字数の上限の境目。
