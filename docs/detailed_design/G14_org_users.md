# G-14 組織・ユーザーの管理

| 項目 | 内容 |
|---|---|
| URL | `/admin/org.php?tab=<departments|users|words>`（GET）、`/admin/org.php?tab=departments&edit=<id>`（課の編集）・`&new=1`（課の追加）、`/admin/org.php`（POST: `action` = `dept_save`・`roles_save`・`word_add`・`word_delete`）、`/admin/user_edit.php`（GET・POST: 追加）、`/admin/user_edit.php?id=`（GET・POST: 編集。`action` = `save`・`temp_password`・`reset_2fa`・`unlock`・`logout_all`） |

## 1. 目的

課、ユーザー、所属、確認者と課長、課別項目の管理者、客先名らしい言葉の一覧を管理する。2 段階認証の初期化やロックの解除など、利用者が自分でできないことを管理者が行う。

## 2. 表示の条件と権限

管理者とシステム管理者補佐（§6.9）。ほかの人は 403。

## 3. 画面の配置

**タブ: 課**

```text
組織・ユーザー
[課] [ユーザー] [注意の言葉]
[ ＋ 課を追加 ]
┌────┬──────┬──────────────────────────┬──────┬────┐
│課   │締め日 │確認者                       │状態   │     │
├────┼──────┼──────────────────────────┼──────┼────┤
│A課  │月末   │[課長 佐藤] [鈴木] [高橋] [田中]│有効   │編集 │
│B課  │25日   │[課長 中村]                   │有効   │編集 │
└────┴──────┴──────────────────────────┴──────┴────┘
```

- 締め日は「n日」「月末」（31）「—」（未設定）。
- 確認者は名前の札で並べ、課長だけ頭に「課長 」を付ける（課長が先、そのあと `sort_order`）。代理・リーダーの区別はない。項目管理者の列はない。

**課の編集（`&edit=<id>`）**

課の編集は、節「基本」（名前・並び順・有効・管理担当）「課長」「引き継ぎ」に分け、ページの中のタブで切り替える（G-21 §5）。保存のあとは、その節に戻る（`#dept-basic`・`#dept-final`・`#dept-succession`）。締め日・管理の仕方・課代とリーダー（確認者）・チェックする人・項目管理者・班・課員の班は、その課の課長が「課の管理」（G-23）で決める（システム管理者は個々の課を管理しない。K-042）。ユーザーの一覧には「班」の列を出し、役割には担当の班も出す（例: 「A課（確認者・山田班）」）。

編集の欄は、課の一覧より上に枠で囲んで出す（「閉じる」で一覧だけに戻る）。ユーザーの一覧には、名前・ID・所属で表を絞り込む欄を出す（JavaScript が動くときだけ。画面の中で行を隠すだけで、送る内容は変わらない）。

```text
A課 の編集                         [基本] [課長] [引き継ぎ]
課長
今の課長: 佐藤
課長 [佐藤（sato・A課・課長） ▼]   [ 課長を保存 ]
（課代・リーダー・チェックする人・項目管理者・班・締め日・管理の仕方は、この課の課長が「課の管理」で決めます）
```

- 候補は有効な利用者全員（その課の人が先、そのあと表示名の順）。
- 課の追加（`&new=1`）は、課の名前・締め日・並び順を入れて「追加する」。

**タブ: ユーザー**

```text
[課: すべて ▼] [有効 ▼] [ID・名前で検索] [絞り込む] [ ＋ ユーザーを追加 ]
┌─────────┬────────────┬────┬──────────────┬────────┬──────┬────┐
│ログイン ID │表示名       │課   │役割           │2 段階認証│ロック │     │
├─────────┼────────────┼────┼──────────────┼────────┼──────┼────┤
│yamada    │山田         │A課  │               │設定済み  │      │編集 │
│sato      │佐藤 [管理者]│A課  │A課（課長）     │未設定    │ロック中│編集 │
└─────────┴────────────┴────┴──────────────┴────────┴──────┴────┘
```

- 絞り込み: 課、状態（有効・無効・すべて。既定は有効）、ログイン ID・表示名の部分一致。
- 並びは課の並び順、表示名の順。無効の人は薄く出す。

**ユーザーの編集**

```text
ユーザーの編集
← ユーザーの一覧
ログイン ID  yamada（追加のときだけ入力）
表示名      [山田]
役職（表示のみ。権限には使いません） [一般 ▼]
所属の課    [A課 ▼]
☐ 管理者
☑ 有効（外すとログインできなくなります。報告は残ります）（編集のときだけ）
[ 保存 ]（追加のときは [ 追加して仮のパスワードを発行 ]）

状態
  2 段階認証       設定済み（2026-11-01 09:00:00）
  ロック           なし
  最終ログイン      2026-11-12 08:55:10
  パスワードの変更  仮のパスワード（未変更）
操作
[ 仮のパスワードを発行 ] [ 2 段階認証を初期化 ] [ ロックを解除 ] [ すべての端末からログアウト ]
```

**タブ: 注意の言葉**

- 説明「自由記述にこれらの言葉が入ると、「客先名や個人名が含まれていませんか」と注意を出します。」と、注意「実際の客先名は入れないでください（この一覧が漏れても客先が分からないように）。」を出す。
- 言葉の入力欄と「追加」。一覧の各行に削除のボタン。

## 4. 表示項目

| 欄 | 内容 |
|---|---|
| 役割（一覧） | その人が確認者・課長になっている課（「A課（課長）」「A課（確認者）」）。項目管理者は出さない。管理者には表示名の横に「管理者」の札 |
| 2 段階認証 | 一覧は「設定済み／未設定」。編集の画面は設定日時も出す |
| ロック | `locked_until` が今より後ならロック中（編集の画面は期限も出す） |
| 最終ログイン | 編集の画面だけ。`access_logs` の `login:ok` の最新 |
| パスワードの変更 | 編集の画面だけ。`must_change_password = 1` なら「仮のパスワード（未変更）」、それ以外は `password_changed_at` |

パスワード、2 段階認証の秘密の値、予備のコードは、どの画面にも出さない（仮のパスワードは発行の直後に 1 回だけ出す）。

## 5. 入力項目と確認

| 項目 | 確認 |
|---|---|
| 課の名前 | 必須、1〜40 文字、一意（「同じ名前の課があります」）。課名には人名を入れないことを推奨（「A課」のような名前） |
| 締め日 | 1〜31（31 は月末）または空欄（なし）。違えば「締め日は 1〜31（31 は月末）にしてください」 |
| 並び順 | 数字。数字でなければ 0 |
| 確認者 | 有効な利用者なら、どの課の人でも選べる。課長は 1 課に 1 人（「課長（最終確認者）は 1 人にしてください」） |
| 項目管理者 | 利用者の ID の形だけを確かめる |
| ログイン ID | 追加のときだけ。前後の空白を除き小文字にしてから確かめる。`@` を含むと「ログイン ID にメールアドレスは使えません」。`^[a-z0-9][a-z0-9._-]{2,31}$` でなければ「ログイン ID は英小文字・数字・. _ - の 3〜32 文字にしてください」。`login_id`・`username` のどちらかと同じなら「同じログイン ID があります」。あとから変えられない |
| 表示名 | 1〜20 文字 |
| 役職 | 一般・主任・課長代理・課長・部長（表示のみ。権限には使わない） |
| 所属の課 | 空（なし）か、有効な課 |
| 注意の言葉 | 1〜20 文字、一意（「同じ言葉があります」）。**実際の客先名は入れない**ことを画面に表示する |

## 6. 操作と処理

| 操作 | 処理 |
|---|---|
| 課の追加 | `departments` に有効で作る |
| 課の編集 | 名前・並び順・有効・管理担当を更新（締め日・管理の仕方は課長が G-23 で決める。新しい課は締め日なし・課全体で作る）。所属する有効な利用者がいれば無効にできない（「所属している人がいるため、無効にできません」） |
| 課長の保存 | 「課長」の節で 1 人を選ぶ（「課長なし」も選べる）。今の課長の行を消し、選んだ人の行を `is_final = 1`・`does_check = 1`・班なしで入れる（その人の課代・リーダーの行は置き換わる）。確認の表示のあと。「課長を保存しました」「課長を外しました」。記録 `admin department:<id>:final`。課代・リーダー・項目管理者は課長が G-23 で決める |
| ユーザーの追加 | 仮のパスワード（12 文字。紛らわしい文字を除いた英数字）を作り、`username = login_id`、`must_change_password = 1` で保存。仮のパスワードはセッションに一度だけ持ち、編集の画面に**1 回だけ**出す（本人に口頭などで伝える）。2 段階認証は本人が初回ログイン時に設定する |
| 所属の変更 | `department_id` を変える。既にある報告の課（`report_records.department_id`）は変えない |
| 無効化 | 自分自身は無効にできない。`is_active = 0`、端末の記憶を消し、`session_version + 1`。同じトランザクションで、確認者・課長・項目管理者の役割（`department_reviewers`・`department_admins`）を外す（退職・異動のため。チェック・コメントの記録は残る）。外した役割を「確認者・項目管理者の役割を外しました: （課名（課長）…）。課長がいなくなった課は、組織・ユーザーの画面で新しい課長を設定してください」で知らせる。報告は残る |
| 仮のパスワードを発行 | 新しい仮のパスワード、`must_change_password = 1`、`failed_count = 0`、`locked_until = NULL`、`session_version + 1`。端末の記憶は消さない。成功のメッセージは出さず、仮のパスワードを出す |
| 2 段階認証を初期化 | 確認の表示のあと、1 つのトランザクションで `totp_secret_enc`・`totp_enabled_at`・`totp_last_step` を NULL、予備のコードと端末の記憶を消し、`session_version + 1`。次のログインで設定し直す |
| ロックを解除 | `locked_until = NULL`、`failed_count = 0` |
| すべての端末からログアウト | 確認の表示のあと、端末の記憶を消し、`session_version + 1` |
| 管理者の付け外し | 自分自身の管理者は外せない。管理者が 1 人もいなくなる変更（外す・無効にする）は不可 |

**権限が意図せず広がる変更を防ぐ**（基本設計書 §15.4）

- 課長の保存のたびに、確認の表示「課長を変えます。課長はこの課の全員の報告（「限定」の項目を含む）を見られるようになります。よろしいですか？」を出す。
- 管理者のチェックを新しく付けたときだけ、「管理者は管理画面（項目・案件・組織・ユーザー・記録）を使えるようになります。報告の中身は、確認者の課の分だけ見られます」と確認を出す（`data-confirm-on`）。

### 6.6 組織の改訂（毎年、と年の途中の役職者の退職など）

組織の改訂は毎年行うほか、年の途中でも役職者の退職などで行う。改訂の前の報告を、改訂のあとも正しい人が見られるようにする。手順は `docs/org_revision.md`。

| 場面 | 作り |
|---|---|
| 課の名前を変える | 課の ID は変わらないので、過去の報告もそのまま新しい名前で見られる（報告に作成時の課の名前は持たない） |
| 課をまとめる・分ける・作り直す | 新しい課の編集で「引き継ぐ課（組織の改訂の前の課）」を選ぶ（`department_successions`）。新しい課の確認者（課長を含む）は、引き継いだ課の報告を、自分の課の報告と同じように見られる（さかのぼれる限り前まで。「限定」は新しい課の課長だけ）。前月との比べ・検索・コメントの一覧にも効く。この課を引き継いでいる課は選べない（輪になるため）。分けたときは、分けた先のそれぞれの課で同じ前の課を選ぶ（どちらの課の確認者も、前の課の全員の報告を見られる） |
| 改訂の前の課を無くす | 課を無効にする（所属する有効な人がいなければ）。報告は残り、引き継いだ課の確認者が見られる |
| 人が別の課に移る | 所属の課を変える。作った報告の課は変えないので、移る前の報告は前の課の確認者が見る（新しい課の確認者は見られない。前の課を引き継いだときは見られる） |
| 役職者が辞める・役を降りる | 利用者を無効にすると役割が自動で外れる（無効化の行）。役を降りるだけなら、課長は管理者が「課長」の節で、課代・リーダーは課長が「課の管理」（G-23）で外す。課長がいなくなった課は、課の一覧に「課長がいません（確認を完了にできません）」を出す |
| 確認者の数 | 「チェック n/m」の m と、G-05 のチェックの欄には、有効な人だけを数える・出す |

### 6.7 管理の仕方（課全体／班ごと）と班

課によって管理の仕方が違う（課全体で見る課もあれば、課長代理ごとの班で見る課もあり、隣の班は見ない）。課ごとに選べるようにする。

| 項目 | 内容 |
|---|---|
| 管理の仕方 | 課長が「課の管理」（G-23）の「基本」で選ぶ（`departments.review_scope`）。`department`（課全体。既定）: 確認者は課の全員の報告を見る。`team`（班ごと）: 担当の班がある確認者は、その班の人の報告だけを見る |
| 班 | 課長が「課の管理」の「班」で足す・名前を変える・無効にする（`department_teams`。課の中で名前は一意）。無効にすると、その班の人（`users.team_id`）と担当の確認者（`department_reviewers.team_id`）の班を外す |
| 担当の班 | 「課の管理」の「確認者と課員」の表の「担当の班」（`department_reviewers.team_id`）。空なら課全体。課長は班を持たない（保存しても空にする） |
| 人の班 | 「課の管理」の「確認者と課員」の表の「班」（`users.team_id`）。その課の有効な班だけ。ユーザーの編集（管理者）では班を変えず、課を移すと班を外す |
| 見える範囲 | 本人の**今の班**で判定する（班を移ると、過去の報告も新しい班の課代・リーダーが見て、前の班は見られなくなる）。課長・課全体の確認者は全員。提出状況・横並び・ホームの未チェックの数・「未チェックを順に見る」・チェックの人数も、見られる報告だけ |
| 管理担当の課 | 課の編集の「この課をシステムの管理担当にする」（1 つの課だけ。`app_state` の `management_department_id`）。この課の課長だけがメッセージ（G-17）を変えられる |
| 課長がいない課 | 課の一覧の札に加えて、管理者のホームに「課長がいない課があります（確認を完了にできません）: （課名）」を出す |
| 記録 | `admin department:<id>:team_add`・`team_update`（課長の操作） |

### 6.8 組織の一括の入れ替え（CSV。タブ「一括（CSV）」）

毎年の組織改訂で、課員の所属・班・役割をまとめて入れる。課員は毎年入れ替わる人もいれば動かない人もいるので、今の組織を出力して、変わる人の行だけを直して取り込む。処理は `app/lib/org_csv.php`。

| 項目 | 内容 |
|---|---|
| 出力 | 「今の組織を CSV に出力」（`/admin/org.php?tab=bulk&csv=1`）。G-10 と同じ形式（UTF-8 BOM、社外秘の見出し 3 行）。1 人 1 行。列は「ログイン ID・表示名・所属の課・班・役割（課長／確認者／空）・担当の班・項目管理者（1／空）・有効（1／0）」。役割は所属の課での役割。記録 `export export:organization` |
| 取り込み | 直した CSV（UTF-8、1 MB まで、2,000 行まで）を選んで「取り込んで、変わる内容を確かめる」。見出しの行より前の行は読み飛ばす。**この時点では DB を変えない**。計画をセッションに置き（30 分まで）、変わる内容（人ごとの「項目: 前 → 後」）と新しく作る班を出す |
| 確かめ | 登録されていないログイン ID（新しい人は先に「ユーザーを追加」）、同じ ID が 2 回、有効でない課の名前、役割・有効・項目管理者の値、所属の課がない人の班・役割、確認者でない人の担当の班、班の名前（40 文字まで）、自分自身を無効にする、課長が 2 人以上になる課（CSV にない人の今の課長も数える）、管理者が 1 人もいなくなる。1 つでも誤りがあれば反映のボタンを出さない |
| 反映 | 「反映する（N 人）」（確認の表示のあと）。1 つのトランザクションで、CSV に載った人ごとに所属の課・班・有効を変え、所属の課の役割（確認者・課長・担当の班・項目管理者）を CSV のとおりにする。無い班の名前は、その課に班を作る（無効の班なら有効に戻す）。課を移る人・無効にする人は、前の課の役割を外す（無効にする人はすべての役割を外し、端末の記憶を消す）。「組織を反映しました（N 人）」。記録 `admin organization:bulk_apply:<人数>` |
| 変えないもの | CSV に載っていない人。所属の課以外の課の確認者の役割（変わる内容に「（所属の課以外の課の確認者の役割はそのまま）」と出す）。表示名（列はあるが、取り込みでは変えない）。新しい人の登録 |
| 補佐が取り込むとき | 管理者・補佐の利用者の行に変わる内容があれば誤りにする（「（ログイン ID）: 管理者と補佐の利用者は、管理者だけが変えられます」） |

### 6.9 システム管理者補佐

管理者が対応できないときに、管理の仕事を代行する役（設計製造開発者とそのサポート役）。`users.is_admin_deputy`。

| 項目 | 内容 |
|---|---|
| 人数 | 有効な人で 3 名まで（`ADMIN_DEPUTY_MAX_COUNT`）。4 人目は「補佐は 3 名までです。ほかの人の補佐を外してから付けてください」。DB のトリガーでも止める |
| 付け外し | 管理者だけ（ユーザーの編集の「システム管理者補佐（n/3 名）」。上限のときは付けられない）。管理者と補佐は兼ねない（「管理者と補佐は兼ねられません。どちらか一方にしてください」）。役が変わった人は、今のログインを切る |
| 代行できること | 組織・ユーザー（課・班・確認者・ユーザーの追加と編集・仮のパスワード・2 段階認証の初期化・ロックの解除・組織の一括 CSV）、案件の管理、項目マスタ（共通・課の項目）、注意の言葉、メッセージ、管理のトップ。代行の開始・終了の切り替えはない（いつでも使える） |
| 見られないもの（個々の情報） | 報告の中身・コメント（確認者でない課。共通編 §10.2 のとおり）、提出状況の人ごとの行（G-08 §2）、横並び、閲覧・出力の記録（G-15 §2）、削除データの中身（件数だけ。戻せない）、2 段階認証・予備のコードの中身 |
| 変えられないもの | 管理者・補佐の利用者（自分を含む。ユーザーの編集を開くと 403、CSV では誤り）。管理者・補佐の役（ユーザーの編集に印を出さず、送られても無視する） |
| 記録 | 補佐の管理の操作・出力は `access_logs.acted_as_deputy = 1`。管理者の管理のトップに「補佐の操作（7 日） n 件」を出す（G-21）。付け外しは `admin user:<id>:deputy_on|deputy_off` |
| 補佐が課に属するとき | 所属の課の部下・確認者としての権限はそのまま（自分の報告、確認者の課の報告） |

## 8. 記録

- 課: `admin department:<id>:create|update|final`。課長の「課の管理」の操作は `settings|members|team_add|team_update`（G-23）。
- ユーザー: `admin user:<id>:create|update|deactivate|temp_password|reset_2fa|unlock|logout_all|admin_on|admin_off|deputy_on|deputy_off`。管理者の付け外しでは、`admin_on|admin_off` のあとに `update`（無効にしたときは `deactivate`）も残す。
- 注意の言葉: `admin word:<id>:add|delete`。
- 仮のパスワードは記録しない。

## 9. 検証の観点

- 一括（CSV）: 出力できる（管理者だけ）。誤りがあれば知らせて反映のボタンを出さない。取り込んだだけでは変えず、反映すると所属・班・役割が変わり、無い班が作られる。違う計画の番号では反映しない（`smoke_org.py`）。

- 管理の仕方と班: 班ごとの課で、課代・リーダーは担当の班の人の報告だけを開け、課長は全員。班を移ると今の班が見る。課を移った人の移る前の報告を、新しい課の課長が開ける。管理担当の課の課長だけがメッセージを開ける。課長がいない課を管理者のホームで知らせる（`smoke_org.py`）。

- 組織の改訂: 引き継ぐ課を設定すると、新しい課の課長が前の課の報告を開け・検索で見つけられる。外すと開けない。輪になる設定はしない。確認者・課長の人を無効にすると役割が外れ、課長がいない課を知らせる（`smoke_features.py`）。

- 管理者以外は開けない・POST できない。
- 課長が 1 課に 2 人にならない（DB の一意の索引でも止まる）。
- 最後の管理者を外せない。自分の管理者を外せない。
- 無効にした人がログインできない。無効化・初期化・全端末ログアウトで、その人の既存のセッションが切れる。
- ログイン ID に `@` を含められない。
- 仮のパスワードが記録・ログに残らない。

### 6.10 組織の改訂の予約（便利機能 G）

年度内の組織改訂は、すぐに発令される場合と事前に予告がある場合があるため、「すぐに反映する」に加えて、反映する日を予約できる。

| 項目 | 内容 |
|---|---|
| 予約 | 取り込んで変わる内容を確かめたあと（誤りがないとき）、「予約して反映する日」（明日から 1 年以内）を選んで「この日に反映するよう予約する」。取り込んだ CSV を `org_schedules` に持つ。記録 `admin organization:schedule:<ID>:create:<日>` |
| 反映 | 予約した日以降の、ログインしている要求の最初の画面の表示（`page_start()`）で反映する。`php app/bin/run_schedules.php` を定期の処理に登録しておくと、だれも開かなくても反映される。同時に 2 つの要求から動いても 1 回だけ（状態を先に変える） |
| 確かめ直し | 反映の時点の組織に対して、取り込んだ CSV をもう一度確かめる（`org_csv_plan()`）。誤りがあれば反映せず「失敗」にし、理由を残す。管理のトップに知らせる |
| 一覧・取り消し | 「一括（CSV）」のタブに予約の一覧（反映する日・人数・状態（予約中／反映済み／失敗／取り消し）・結果・予約した人）。予約中は「取り消す」 |
| 補佐 | 補佐が予約したときも、反映の時点で管理者・補佐の利用者を変える行は誤りにする（§6.9） |
